# Security

What protects the shop, how it works, and what the owner must do. Each item has a test in `test/`.

## The private admin link (BUH-02.08)

The Admin Hub is not on the public site. Nothing in the shop's pages, scripts, `/sw.js`, `robots.txt` or the sitemap names it (no button, tab, route name or "admin" string; the only "admin" in the shop's scripts is inside Firebase's own error messages). It is served at one private path, and every admin address answers exactly like an address that does not exist until the browser has been through that path. Tested by `test/admin-door.test.mts` and `test/admin-door-e2e.test.mts`.

| What | How |
| --- | --- |
| **The link** | One path segment of 24 random bytes (192 bits) in base64url, 32 characters: `https://yourdomain.ae/k7Qm2vXa9pTeLr4w…`. Made on the first start, or by the update that brought private links (atomically: when two copies start together, one makes it). |
| **Only its hash is kept** | The database (kv `admin:link`, in backups) holds SHA-256 of the segment with a purpose prefix, plus a random version. A copy of the database or a backup does not reveal the link. Checks hash what was asked for and compare digests with `timingSafeEqual`. |
| **Shown once** | On the console, in a box next to the first password (`podman logs beautifuluaehome`; it stays in that container log, and in journald under Quadlet, until the container is removed, so keep the server's login private), and emailed to the admin email when email is set up. `logEvent` lines only ever carry the first 4 characters. The answer to "Change the admin link" carries the new link once. |
| **The door cookie** | Visiting the link sets `buh_door`: `HttpOnly`, `SameSite=Strict`, `Secure` in production, path `/`, 30 days, renewed at most once a day while used. It is a token signed with the server's key (`SESSION_SECRET` or `DATA_DIR/session.key`) and bound to the link's version and hash. |
| **Unknown without the door** | Every `/api/admin/…` address (sign-in, passkeys, recovery codes, forgot and reset password, versions, events, stock, all of them), `/api/courier/dispatch`, `/test`, `/live` and `/sandbox-check`, without a valid door cookie, are handed to Next.js as an address that does not exist, so the answer is the shop's ordinary 404, byte for byte the same body and headers as any unknown `/api/…` address. Only then do the normal checks (session, same-site, password) apply. |
| **Guessable paths** | `/admin`, `/login`, `/wp-admin`, `/dashboard`, `/administrator`, `/admin.php`, `/.env` and the hub page's internal name (`/hub`) are the ordinary 404, byte for byte the same as any unknown address. |
| **Central, and checked twice** | The door is checked at the HTTP server itself, before Next.js routes the request (`src/lib/server/frontGate.ts`, installed at start by `src/instrumentation.ts`): a Next.js proxy's rewrite leaves its own headers on the answer, which would tell a 404 apart, and a proxy that runs for every request costs the storefront. Every admin route also calls `requireDoor` (directly or through `requireAdmin`), so a request that ever reached one another way still gets a 404; a test lists every route file under `src/app/api/admin` and checks both (the code, and over HTTP that each method answers like an unknown address without the door, with or without a session). Paths are normalised first (`/api//admin`, `/api/%61dmin`, dot segments). |
| **Headers on the link** | `Referrer-Policy: no-referrer` (the link never leaves in a Referer), `X-Robots-Tag: noindex, nofollow`, `Cache-Control: no-store`, and `<meta name="robots" content="noindex, nofollow">`. |
| **Service worker** | Never answers, caches or even recognises the link: it handles only the shop's own pages (`/`, `/p/…`), and leaves alone every file requested without a referrer (the hub's, which are sent with no-referrer). |
| **Changing it** | Settings → Security → **Change the admin link**: the current password (counted like a sign-in attempt) or a passkey sign-in in the last 10 minutes. A new segment and version: the old link and every door cookie stop working at once, in every running copy; the browser that changed it gets a new door. The new link is in that answer only, and emailed. Audit log `admin.link_changed`, never the link. |
| **Lost it** | Because only a hash is kept, the link can never be printed again. `podman exec beautifuluaehome node scripts/admin-link.mjs --new` (shipped in the image, no code on disk) makes a new one and prints it; the old one and every door stop working; the change is audited. Without `--new` it only says when the link was made. |
| **Password-reset email** | The emailed link is `https://yourdomain.ae/<grant>#reset=<token>`: the path is a separate single-reset door grant (32 random bytes, only its hash stored with the reset link, valid while the reset link is), so the reset works on a phone that never had the admin link; the token stays in the fragment. Setting the new password, or the 30-minute expiry, ends the grant, and the door it gives lasts only that long (not 30 days). It is not used up by the first visit, because mail apps check links before the owner opens them. |
| **Passkeys** | Unchanged: the WebAuthn ceremony runs on the same origin; its routes are behind the door like every other admin route. |
| **Updating an existing shop** | The update makes the link: printed once, emailed (when email is set up), and for an owner who was signed in at that moment (a session older than the link), opening the shop sends them to it once (a 303 with no-referrer). That one-time copy is encrypted with the server's key, never in backups, deleted once shown or after 8 hours. Existing admin sessions carry on. |
| **Backups and restore** | Backups keep the link's hash (a restored shop keeps the owner's bookmark), never the one-time copy. A backup from before BUH-02.08 has none: the first start makes and prints a new link. If the link was changed after the backup was taken, make a new one after restoring. |
| **Access logs** | The proxies mask it: Caddy (`deploy/shop-snippets.caddy` for the access log, and the global `log` block of each Caddyfile for Caddy's own messages) and nginx (`log_format buh_masked`) log only its first 4 characters, no Referer, and no `Location` (the one-time move of a signed-in owner to a new link is a redirect to it). nginx's error log cannot be filtered (it repeats the request line), so the nginx site keeps it at `crit`. Checked against caddy 2.8.4 and nginx 1.27 with the shop down (the case where the request is logged as an error). |
| **Limits** | The link is a second lock, not the only one: the password, passkey or recovery code is still needed. Anyone who has the link and a door cookie still meets the sign-in. Keep the link private like a password; change it when in doubt. |

## Scanner slow-down

With `TRUST_PROXY=1` (behind the shop's proxy, which sets the real address), an address that gets 10 "not found" answers in a minute waits 1 s per request, and at 30 in a minute gets `429 Too Many Requests` (with `Retry-After`) for 10 minutes, on every address of the shop. Counted: 404s to pages and to admin addresses. Never counted: the shop's own files (`/_next/…`, a missing photo, an icon) and the public APIs, which an old page left open across an update can ask for by the dozen; a taken-down product (`/p/…`, which search engines and old shares ask for); and a 404 to a browser holding a valid door (the hub asking for a deleted order). A hub tab left open after the link was changed stops calling at its first unknown-address answer and says so, well under 10, so it can never shut its owner out. A shopping visit has no such 404 at all. The counts live in a map of their own in the shop's rate limiter (at most 50,000 addresses, the least recently seen dropped first), so a flood of 404s from many addresses can never push out the sign-in or phone counters. Without `TRUST_PROXY` nothing is counted (every visitor would look the same). Tested in Chromium too: a whole visit at 375 px never meets a 429.

## Admin hub

| What | How |
| --- | --- |
| **Sign-in checked on the server** | `/api/admin/login` verifies an scrypt hash (N=16384, r=8, p=1). Nothing about the credentials is sent to the browser. Older builds shipped the password in the page and trusted a `localStorage` flag; both are gone, and leftover keys are deleted on first load. |
| **First start** | With no `ADMIN_EMAIL` / `ADMIN_PASSWORD_HASH`, a random one-time password is printed to the server log once, as the server starts. It must be changed at first sign-in; until then every other admin call is refused. |
| **Managed from the environment** | Set `ADMIN_EMAIL` and `ADMIN_PASSWORD_HASH` (from `npm run hash-password`) to manage the account outside the app. |
| **Wrong passwords** | Wrong recovery codes count together with wrong passwords. 5 in 15 minutes from one address pause sign-in for that email from that address for 15 minutes, so a stranger cannot lock the owner out from somewhere else. 50 in an hour from anywhere pause it everywhere (a spread-out guess). While paused, the password is not checked at all, so a pause never reveals that a guess was right. Unknown emails get the same answers, so they reveal nothing about which accounts exist. Behind nginx with `TRUST_PROXY=1`; without a trusted proxy every visitor counts as one address. |
| **Throttling** | 30 sign-in attempts per 10 minutes per address in the app; 10 per minute in nginx. |
| **Sessions** | HMAC-signed cookie: `HttpOnly`, `SameSite=Strict`, `Secure` in production, 8 hours. **Sign out** ends every session on the server (a copied cookie stops working), and so does changing the password. Rotating `ADMIN_PASSWORD_HASH` ends sessions too. The session generation starts at a random number in a new or restored data folder (backups never carry `session-state.json`, `session.key` or `admin.json`), so a cookie from before a restore can't come back to life even when `SESSION_SECRET` and `ADMIN_PASSWORD_HASH` are unchanged. |
| **Every admin route checks it** | Courier dispatch, test, Live switch and Sandbox check, SMS test and the AI studio all call `requireAdmin` on the server (which checks the door first). |
| **Roles (BUH-02.17)** | Two roles: `owner` (everything) and `accountant` (read-only). `requireAdmin` denies by default: only the owner passes unless a handler names the accountant (`requireReader`). The accountant's allow-list is GET only: reports and their ZIP, expenses (list, versions, bills, categories), a bank-transfer screenshot and an order's receipt/tax invoice, the audit log and its export, VAT settings (read) and the VAT return and its CSV. Settings, keys, orders, customers, chats, stock, prices, invites, the admin link, passkeys and every write are refused (403, before anything runs). `test/accountant-routes.test.mts` calls every handler of every admin route file with an accountant session and fails on any change to that list. The hub shows an accountant only Money. |
| **Accountant accounts** | Invited by the owner (`staff_accounts`): a one-time setup link (32 random bytes in the fragment, plus a 256-bit path grant that opens the hub's door only while the invite is open), stored as hashes, 72 hours, used once. The accountant then signs in at the owner's private link with the same form, the same scrypt hashing and the same pauses. Their session cookie carries the role, the account, its generation and a fingerprint of its password, all signed; each request checks the account in the database, so **Revoke** (or a new setup link) ends their sessions at once in every running copy. Signing out ends only their sessions; the owner's sign-out ("sign out everywhere") ends every accountant's too. A data folder restored from a backup starts a new staff-session epoch (`staff-session-state.json`, never in backups), and the restore script revokes every accountant account it brings back (the backup may be older than a revoke): written to the audit log on the first start (`accountant.revoked_by_restore`), and the hub says "Re-invite your accountant". A revoked account invited again counts towards the limit of 10. **Doors:** the door the setup link's path gives carries a hard end (the invite's 72 hours) that a renewal keeps, and is bound to the account and its session generation, like the door the setup gives that browser: a revoke, a new setup link or a sign-out everywhere ends them at once (the door check reads the account as the session check does). A password-reset email's door is capped the same way. The owner's door (from the private link) is unchanged.
- **What an accountant can see.** Everything in Money, which includes personal data: customers' **bank-transfer screenshots** (names, banks, account numbers as the customer's app shows them); **customer names** (sales.csv and vat-return.csv in the exports, and on each tax invoice, with the customer's email when given; sales.csv has name and emirate, no phone or address); and the **full audit log**, including sign-in **IP addresses** and **passkey/device names** (customer phone numbers and emails in it are masked). Invite only someone you would show your books to. No passkeys, recovery codes or password reset for accountants. The link reveal after an update is shown to the owner only. Invites, setup, sign-ins, revokes and exports are audited (sign-ins before the session is given). |
| **Cross-site requests refused** | State-changing calls must come from this site (Origin / Referer / Sec-Fetch-Site, compared with the `Host` header; `X-Forwarded-Host` is never trusted), in addition to `SameSite=Strict`. |

## Admin password reset and email settings

- **Forgot password?** gives the same answer, just as fast, for any email: the email is sent after answering, so neither the words nor the timing reveal the admin email. Limited to 5 an hour per address, and at most 3 links an hour are sent for the account; asking again never cancels a link already sent, so a stranger can't lock the owner out of recovery. Each link holds a random 256-bit token; only its SHA-256 is stored, it works for 30 minutes, and using any one ends the others, every session and any sign-in pause. Accounts set by `ADMIN_EMAIL` get no link.
- The token is in the link's fragment (`/<grant>#reset=…`), which browsers never send to a server, so it stays out of access logs; the page removes it from the address bar at once. The path is the single-reset door grant (above).
- Changing the sign-in email needs the current password (counted like a sign-in attempt) and ends other sessions.
- The SMTP password is write-only, and is dropped when the server changes. A mail server typed in Settings must resolve to a public address (no loopback, private or cloud-metadata ranges), the shop connects to the address it checked, and the certificate is checked against the name. Ports: 25, 465, 587, 2525.

## Getting back in: recovery codes and passkeys

| What | How |
| --- | --- |
| **Recovery codes** | 10 per set, each 16 characters from a 32-letter alphabet without 0/O/1/I (80 random bits from `crypto.randomInt`), shown as `XXXX-XXXX-XXXX-XXXX` exactly once. Only a SHA-256 of each code is stored (table `admin_recovery_codes`): 80 random bits can't be guessed back from a hash, so a slow hash would only cost CPU per sign-in. A new set replaces the old in one transaction. |
| **Who can create codes** | A signed-in owner who types the current password again (counted like a sign-in attempt), or who signed in with a passkey in the last 10 minutes. A stolen session cookie alone can't mint a way back in. A wrong password is answered 400, so the owner stays signed in. |
| **Using a code** | Email + code at `/api/admin/login/recovery`. The code is used up by one `UPDATE … WHERE code_hash = ? AND used_at IS NULL`; SQLite applies it once, so a code works once even with two copies of the shop sharing the database (tested with two processes racing). Wrong codes count towards the same pause as wrong passwords (same keys, same limits); while paused the code is not looked at, so a pause reveals nothing and doesn't use a code up. A wrong email never reaches the codes. |
| **After a code** | Every other session ends. The new session lasts 30 minutes and can do one thing: choose a new password (same rules as a reset), without the forgotten one. The admin email is told a code was used (when mail is set up); the audit log records it with the address and how many are left, never the code. |
| **Codes when the password is in the environment** | With `ADMIN_PASSWORD_HASH` the password can't be changed in the app, so **a recovery code is a full key to the Admin Hub for 30 minutes**: orders, settings, couriers, everything. What that session can't do is change the ways in: adding, keeping or removing a passkey and creating new codes all need the current password (or a passkey sign-in in the last 10 minutes). Keep the codes as safe as the password itself. |
| **New password after a passkey** | Within 10 minutes of a passkey sign-in, the owner may choose a new password without the old one (Settings → Passkeys & recovery codes → Forgot your password?): the passkey's fingerprint/face/PIN check just proved it's them. After that, the current password is needed again. |
| **Passkeys** | WebAuthn via `@simplewebauthn/server` / `@simplewebauthn/browser` (exact versions). Only discoverable passkeys with user verification (fingerprint, face, PIN) are made and accepted; no attestation is asked for. Only the public key, counter, transports and a name are stored (`admin_passkeys`). Adding one needs the current password; removing one (effective at once) needs the current password or a passkey sign-in in the last 10 minutes. Adding one emails the admin. |
| **Which domain** | The relying-party ID and origin come from `NEXT_PUBLIC_APP_URL`, which must be `https://` (or `http://localhost`) and a domain name, never an IP. They are never taken from a request header, except that with no `NEXT_PUBLIC_APP_URL` a request whose `Host` is `localhost` may use `localhost` (a passkey for localhost only works in a browser on the same machine). Each passkey remembers the domain it was made for and only signs in there. |
| **Challenges** | Random, kept server-side (`webauthn_challenges`) for 5 minutes, used up by the first answer (`DELETE … RETURNING`, so a replay fails), and tied to the browser by an `HttpOnly`, `SameSite=Strict` cookie holding the challenge id and an HMAC of it. Adding a passkey is also tied to the session that asked. At most 10,000 live challenges; when full, the oldest sign-in challenges are dropped to make room, so starting a passkey sign-in is never refused. There is deliberately no shop-wide limit on it (a stranger could use one up and block the owner); a per-address limit applies behind a trusted proxy. Challenges are left out of backups. |
| **Copied passkeys** | When an authenticator keeps a signature counter, a counter that does not go up means a copy exists: the sign-in is refused, logged, audited and emailed to the admin. This is checked only after the signature is verified, so a forged answer can't set off alerts. Synced passkeys (iCloud, Google), which always report 0, are unaffected. |
| **Passkey sign-in during an attack** | A passkey can't be guessed, so a pause caused by wrong passwords or codes does not block it, and no shop-wide counter can be used up to block it: the owner still gets in while someone attacks the password. (To push out the owner's own challenge in the seconds a sign-in takes, an attacker would have to start thousands; the owner simply tries again.) The session is the same as after a password sign-in, and audited as `admin.sign_in` with `method: passkey`. |
| **After a restore** | A backup can be older than a passkey the owner removed (a lost phone) or a new set of codes, and nothing in it can tell. So `scripts/restore-backup.mjs` voids every restored recovery code and switches every restored passkey off (they stay listed; a sign-in with one is refused) until the owner, signed in with the password, presses **Keep** (password needed) or **Remove**. It prints a warning, and the Admin Hub shows a banner until the owner presses **Done**. This can't lock the owner out: a restore never brings back the admin account, so there is always a fresh one-time password in the log, or the `ADMIN_PASSWORD_HASH` password. A revocation stamp kept outside the backup was considered and rejected: a restore with `--replace` moves the whole data folder aside, and a restore onto a new server has nothing to compare with, so a stamp would protect only some restores. |
| **Only WebAuthn fields** | Every new route uses `readJsonBody` (size-capped), refuses unknown fields, and passes the library only the fields WebAuthn defines (base64url, length-capped). |

## Version switching from the Admin Hub

- The shop never controls Docker or Podman. It writes one line (`rollback 2.0.1` or `update`) to a request folder shared only with the updater, creating the file new (no overwrite, no links) and only one at a time. Admins only, 10 an hour, written to the audit log.
- The updater first moves the request into a new folder only it can open, so it can't be swapped for a link or a pipe while being read; it then accepts only a small plain file whose line matches `rollback N.N.N` or `update` exactly, and refuses versions before 2.0.0. Anything else is dropped unread and never echoed. The folder is sticky and not listable, so the shop can't remove or read anything else there.
- The updater's status comes back through a second folder the shop mounts read-only; it holds versions and messages, no secrets. The updater writes it to a new file and renames it, so a planted link is replaced, never followed. The shop reads it defensively (size cap, links refused, fields checked).

## Settings: autosave and the last good configuration

- Every save (typed or automatic) is validated on the server; an invalid change is refused and the stored settings are unchanged. Autosave never sends passwords or keys (blank means "keep the saved one"); only Save does.
- New mail settings are tried (SMTP login) before they are stored; if that fails while the current settings are known to work (a passing trial or test email), the change is refused (409). Known-good is kept as a hash, never a copy of the password.
- Autosaves within 2 minutes of each other are one history entry; Undo restores the entry before the session, and the restore itself is kept, so it can be undone.

## Looks (Settings → Look)

- `PUT /api/admin/look` (`{ preset, mode }`) and `POST /api/admin/look` (`{ switchBack: id }`): `requireAdmin`, `readJsonBody` (1 KB / 256 B), `allowFields`, `handleRouteError`. The preset and mode are checked against allow-lists on the server; the time is the server's and the author is the signed-in admin (neither is accepted from the browser). Every change is audited (`look.changed`, `look.switched_back`) and kept in the settings history; the look from before looks existed is pinned there and never pruned.
- `/look.css` is public (the colours of the chosen look, nothing else) and computed from the allow-listed preset and mode only, so no text the owner types reaches it. It is linked in every page's head, which keeps the storefront a static page (a per-request page would cost the same as a nonce CSP, below); `max-age=0, must-revalidate` with an ETag, so an unchanged look is a 304.

## Delivery charges

- Whether we deliver, and any same-day charge, are decided on the server from the address and Settings → Delivery, in fils; a GPS reading never decides it (devices often report a network location). The area is free text (up to 120 characters); the suggestion list and a GPS-suggested area are conveniences in the browser, never trusted by the server. GPS suggests an area only from a reading within 300 m accuracy and 1.5 km of a known community, and no map tiles or other third parties are loaded. The browser's total must match the server's or the order is refused before anything is charged; a same-day order after the cut-off is refused (409) and checkout moves back to standard.

## Chat

- Each chat has a random id and a 192-bit secret kept in the customer's browser; only its SHA-256 is stored, and it travels in a header or the request body, never in an address. A wrong secret and an unknown chat get the same answer.
- Starting chats is limited per address (6 an hour) and shop-wide (300 an hour); messages to 40 per 10 minutes per address; a chat holds at most 300 messages of up to 1,000 characters. Text is shown as text, never as HTML.
- The owner is emailed at most once every 5 minutes per chat. Subjects carry only the chat's key and the customer's name/contact after control characters are removed.
- **Replies by email:** the mailbox (IMAP over TLS, port 993) is read once a minute. A server typed in Settings must resolve to a public address; the shop connects to the address it checked and verifies the certificate against the name. Only mail whose subject has a known `[Chat #KEY]` (10 random characters) is used, only the new text (not the quote), at most once per Message-ID. It counts as the owner's reply only from the owner's addresses (backup address, sign-in email, sender), and is refused when the receiving server reports DMARC failure (or SPF and DKIM both failing); otherwise only from the customer's own email, as the customer. The mailbox password is write-only and dropped when the server changes.
- The assistant answers only from the owner's text and the size presets; it never composes prices, discounts or promises.
- Owner replies and status changes are in the audit log; chats are in backups.

## Checkout phone check: WhatsApp (free) by default

Settings → Phone check is **WhatsApp (free)** for new and existing shops: checkout sends no code, and the customer's one WhatsApp message (or the owner's phone call) confirms the order. A code used to cost an attacker an SMS round trip; now nothing does, so:

- **The number is still checked on the server** (`validatePhone`: UAE mobiles only, the same rules as below) and is **never treated as verified**: such an order has `phoneVerified: false`, and the hub shows it as awaiting confirmation until the owner taps **Confirmed on WhatsApp** or **Confirmed by phone call**.
- **Caps on orders not yet confirmed** (they hold pieces): at most **2 per phone**, **4 per connection** (the address kept only as a SHA-256 hash on the order, in `card_ip`, when it is known: `TRUST_PROXY=1`; an IPv6 address counted by its **/64**, since one home or phone can pick any address in it; the same for the card caps) and **60 across the shop** (the customer is told politely the shop is busy). **Without `TRUST_PROXY`** the shop can't tell connections apart, so there is no per-connection cap and the shop-wide one is **15**; Settings → Phone check says so. Orders proved by a code, and card orders (they have their own caps, below), don't count. On top: 20 orders per address per hour, 3 waiting orders per phone.
- **A small bag, and never most of a size:** an order no code proved takes at most **2 of each item and 5 lines** (as an unverified card order), and orders not yet confirmed hold at most **half of a size's pieces** (counting the ones they hold; at least 2, so a one-of-a-kind piece can still be ordered); beyond it, `409 popular_piece` ("This piece is very popular right now — please message us on WhatsApp"). All checked inside the transaction that reserves the stock.
- **The owner is told:** at 80% of the shop-wide cap, and whenever it refuses a customer, the shop logs it, emails the admin address (at most every 6 hours each) and the monitor shows a problem (Settings → System, the monitor's emails).
- **Unconfirmed orders cancel themselves** after the set hours (default 24, 2 to 168), and sooner when the customer never opened WhatsApp (default 6 h, 2 to 48, never later than the first; both times fixed on the order when it is placed, migration 11's `wa_cancel_at` and `wa_unopened_cancel_at`): every 5 minutes the server claims each due order with one conditional `UPDATE` (so two copies of the shop can't both cancel it), puts its pieces back once, and writes `order.auto_cancelled_unconfirmed` (with `why`: `not_confirmed` or `whatsapp_never_opened`) to the audit log inside the same transaction. Not cancelled: confirmed orders, orders the owner chose to ship anyway (that clears both times in the same audited transaction), paid card orders, and **bank transfers**: their private page lasts 14 days, so at the deadline one with neither screenshot nor payment is flagged for the owner instead ("Bank transfer not confirmed after 24 h — check your bank, then cancel or confirm", audited as `order.bank_unconfirmed_flagged`, emailed), its pieces still held; one with a screenshot or payment has its time cleared (the owner decides).
- **A cancelled or delivered order is never confirmed afterwards:** `confirmed`, `call`, `use_sender` and `correct_phone` answer 409 ("Auto-cancelled at … — ask the customer to place a new order"), so a tap can't revive an order whose pieces are back on sale; `call` only for an order still waiting.
- **No SMS can be pumped:** `/api/otp/send` answers 409 in WhatsApp mode, even with a gateway saved, and Firebase's route is closed (the public settings carry no Firebase config).
- **Card orders** behave as "no SMS gateway": no code, at most 2 of each item and 5 lines, the unpaid-card caps below; paying is the proof.
- **Shipping an unconfirmed order:** booking a courier (or confirming by hand) for a cash-on-delivery order no code proved and not confirmed answers `409 whatsapp_unconfirmed`; the owner's explicit "ship anyway" (`shipUnconfirmed: true`) is written to the order's history and the audit log (`order.ship_unconfirmed`) before anything goes to a carrier. "Hold until confirmed" still refuses outright.
- **No WhatsApp number set:** nothing can confirm an order, so orders are still taken but flagged for the owner ("call the customer"), never verified and never auto-cancelled.
- **"Use the number it came from"** (the owner's fix after a mismatch): the typed number is validated like checkout's, the order's phone (JSON and indexed column) is changed, the old one kept in the order's history, and `order.phone_changed` audited in the same transaction before it is confirmed.
- **During an update** (old and new versions share the database for a minute): orders placed without a code are plain JSON every version reads (`phoneVerified: false`); the new columns (migration 11: `phone_check_method`, `wa_cancel_at`, `wa_unopened_cancel_at`) are ignored by an older version, which then simply never auto-cancels them. A page from before that sends an expired code with no number gets the old "verify again" answer; its code request is told to reload.

## Checkout phone verification (Phone check "SMS code")

- **UAE mobiles only** (50, 52, 54, 55, 56, 58; `OTP_ALLOWED_PREFIXES`, default `+971`). Every way of writing a number (spaces, `00971`, `+971 0…`, Arabic digits) maps to one number and one set of limits. Other countries are shown the support email instead.
- **Codes:** 6 digits from `crypto.randomInt`, valid 10 minutes, single use, 5 guesses. Only an HMAC of each code is kept.
- **Limits against SMS-pumping fraud:** 1 code per number per 30 s and 5 per hour; 10 per address per hour; `OTP_MAX_PER_HOUR` (default 300) for the whole shop.
  - All limits are checked together and counted only when all allow the send, so a refused request uses up nothing.
  - The shop-wide counter cannot be pushed out of memory by a flood of other keys.
  - Reaching the shop-wide cap is written to the audit log (at most hourly).
- **If SMS is unavailable**, the gateway is down or the cap is reached, checkout cannot complete, by design: orders need a verified number. Customers are told to try again or email the shop, and the server log warns at start-up when no gateway is configured.
- **The browser cannot choose the gateway.** The public endpoint ignores any gateway settings in the request and uses the server's environment only. Older builds would post the code to any URL a caller supplied.
- **No code in the browser in production.** With no gateway configured, test mode shows the code on screen, but only outside production (or with `OTP_DEV_MODE=true`).
- **Firebase Phone Authentication (optional).** Google sends and checks the code; the browser then posts a Firebase ID token to `/api/otp/firebase`. The server verifies it with Node's crypto (no Firebase SDK on the server):
  - RS256 only, with a key id Google publishes (certificates cached for their `max-age`, refetched at most once a minute for an unknown key id, 10 s timeout);
  - issuer and audience must be this shop's project, so a token from any other Firebase project is refused;
  - not expired, not issued in the future (60 s skew), signed in by phone within the last 10 minutes, with a `phone_number`;
  - the number must still be a UAE mobile. The answer is the same signed phone token as the shop's own codes.
  - The route is closed unless Firebase is the switched-on SMS option, is same-origin only, size-capped and limited to 30 attempts per address per 15 minutes. Firebase's own abuse limits apply to sending; the shop's per-number send limits do not.
  - The web config (API key, auth domain, project ID, app ID) is public by design. Protect the project in Firebase: authorized domains set to the shop only, a Google Cloud budget alert, and (optionally) SMS region policy allowing only the UAE.

## Confirm on WhatsApp (BUH-02.09)

- **No third party.** A plain `https://wa.me/<shop number>?text=…` link: the customer's own WhatsApp sends the message, the owner reads it in theirs. No WhatsApp Business API, no unofficial WhatsApp library (those break WhatsApp's terms and get numbers banned), no data leaves the shop.
- **What it proves:** the person who sent the message holds the WhatsApp account of the number the owner sees as the sender. The owner compares that with the order's phone (shown next to the buttons) before tapping **Confirmed on WhatsApp**. It doesn't prove anything by itself: the shop never sees the message.
- **The code is not a password.** 4 digits from `crypto.randomInt`, made by the server with the order, shown to the customer and to anyone who has the order number and its phone (Track Order). It only ties a message to an order. It is kept in the order's own columns, never in the server log or the audit log (`logEvent` also redacts any `code` field).
- **The owner's answer** (`POST /api/admin/orders/<id>/whatsapp`): `requireAdmin` (private-link door, session, same site), a 1 KB body with allow-listed fields (`result`: `confirmed`, `mismatch`, `call`, `use_sender` or `correct_phone`; `phone` only with `use_sender` or `correct_phone`, validated with `validatePhone`; the hub shows the number normalised by the same rules, `src/lib/phoneNumber.ts`, before the owner confirms), the order looked up on the server (unknown: 404). Idempotent: the same answer again changes nothing. The audit entry is written inside the same transaction, so an answer is never saved or reported done without it. A phone change (`use_sender`, or a later `correct_phone`, refused on cancelled and delivered orders) keeps the old number in the order's history (`order.phone_changed`, masked in the audit log); Track Order accepts the current number or any number in that history.
- **Hold until confirmed** (off by default) is enforced on the server: confirming or booking a courier is refused until the order is confirmed; cancelling always works.
- **"Customer opened WhatsApp"** (`POST /api/orders/whatsapp-opened`): same site, 1 KB, needs the order number and the phone on it (like Track Order), only sets that order's "opened" time once, answers `{ ok: true }` whether or not the pair matched (no oracle), 10 per order and 30 per address per 15 minutes.

## Card payments: Stripe (BUH-02.09)

- **No card data touches the shop's server (PCI DSS SAQ A).** Card numbers are typed into Stripe's own fields (Payment Element and Express Checkout Element, in frames from `js.stripe.com`); Apple Pay and Google Pay hand Stripe a token. The shop only ever sees Stripe's PaymentIntent id, the card brand and last 4 digits, and the wallet's name, phone and address (which the customer chose to share). Stripe.js is loaded only at checkout, only when card payments are on, from its own chunk (the first load never has it).
- **Amounts on the server only.** The order is priced from the catalogue on the server (fils, AED), exactly as for cash orders; the server creates the PaymentIntent for that total. A total, price, fee or amount from the browser is never used (a mismatching `expectedTotal` is refused before anything is charged).
- **Card payment fee** (Settings → Payments `cardFeePercent`, 0–10 with up to 2 decimals, validated on the server; default 3.5): added on the server to card orders only, `round(items + delivery in fils × percent / 100)` half up in integer maths, stored on the order (`cardFee`, `cardFeePercent`) and included in its total, so the PaymentIntent, the webhook's amount check and refunds all use total + fee. A browser total without it is refused (409 `price_changed`, with the current percent). A change of the percent (or of the bank-transfer choice) is audited with from, to and who (`settings.payment_options_changed`).
- **One intent per order, one refund per order.** Stripe idempotency keys `order:<id>` and `refund:<id>` (with the amount when only the rest is refunded after a partial dashboard refund, and a try number after a refund that failed): a retried or doubled request gets Stripe's first answer back. The checkout reference still makes one checkout attempt one order; a declined attempt is closed (stopped at Stripe, pieces back on sale) and the next try is a new order. When the outcome is unknown (the browser lost its connection, or couldn't reach the shop to close the attempt), the browser keeps the checkout reference, so a retry returns the same order and the same PaymentIntent (or, once paid, the paid order): never a second charge. It says "Nothing was charged" only for Stripe's `card_error` / `validation_error`.
- **Paid only on Stripe's word.** `payment_intent.succeeded` from the webhook, or the server retrieving the PaymentIntent from Stripe (when the customer's confirmation screen asks), and only if its id is the one stored on the order, `metadata.orderId` matches, the currency is `aed` and the amount is the order's total in fils. Otherwise it is recorded as a mismatch (audited, logged as an error) and the order stays unpaid. The browser's "it worked" is never taken as paid.
- **The webhook** (`POST /api/stripe/webhook`) is public by nature (Stripe calls it), so it trusts only the signature: Stripe's library checks every `v1` signature in the `Stripe-Signature` header over the raw body (before anything is parsed) with the saved signing secret, comparing in constant time (`crypto.timingSafeEqual`); a timestamp more than 5 minutes old (a replay) or more than 5 minutes ahead is refused. No secret saved, a wrong signature, a body over 256 KB, or anything malformed: the same `400 {"received":false,"message":"Invalid request."}`. Rate-limited per address and in total. Each event is applied once.
- **The webhook address is public by design, and invisible to scanners.** Stripe must be able to reach it, so it can't be hidden like the Admin Hub; what protects it is the signature, which only someone holding the saved signing secret can make. To a scanner it isn't there: the front gate (`decide()` in src/lib/server/frontGate.ts) hands anything but a `POST` carrying a `Stripe-Signature` header (a `GET`, a `HEAD`, a bare probe) on as an unknown address, so it gets the same 404 as any address that doesn't exist, byte for byte, and counts towards the scanner slow-down. A request that does carry a signature but fails the check still gets the route's 400, so Stripe's dashboard shows a failed delivery to the owner.
- **Each event once, whatever the order.** Event ids are stored (`stripe_events`) in the same transaction as their effect, so a resent event changes nothing; a paid order can't be un-paid by a late `payment_failed` or `canceled`; every change is conditional in its `UPDATE` (safe with two copies of the shop running during an update). A change is written to the audit log inside its transaction: if the log can't be written, nothing is saved and Stripe retries.
- **Unpaid card orders** (status `pending_payment`) hold their pieces for 10 minutes; then, or on `payment_intent.canceled`, or when the customer leaves card checkout (proved with the client secret only that browser has; only its hash is stored), the payment is cancelled at Stripe first (if Stripe says it was paid meanwhile, it is recorded as paid instead) and the order cancelled with its stock released exactly once. With an SMS gateway on, card orders prove the phone with a code like every order. Without one, no code is asked, so an unverified card order takes at most 2 of each item and 5 lines, and there are at most 2 unpaid card orders per phone, 3 per connection (when the address is known, `TRUST_PROXY=1`; kept as a SHA-256 hash on the order) and 30 in total (the customer is told politely that card checkout is busy).
- **Keys switched between test and live** (or the secret key removed): the PaymentIntent's mode (`livemode`) is stored on the order. An unpaid order the saved key can't reach (other mode, no key, or Stripe answers `resource_missing`) can't be charged through this account: it is cancelled and its stock released once, audited with the reason (a live one is flagged for the owner to check that dashboard). A paid one can't be refunded through the shop: **Cancel without Stripe refund** (`withoutStripeRefund: true` and `confirm: "refund-in-stripe-dashboard"`) is accepted only then, audited before it counts, and leaves a note to refund it in that Stripe dashboard. Saving keys of another mode while card orders are open warns (never blocks).
- **Owner actions:** card orders can't be marked paid by hand, confirmed or booked before Stripe says paid, or cancelled without the refund. **Cancel & refund** (`POST /api/admin/orders/<id>/refund`): `requireAdmin`, 1 KB body with allow-listed fields (the amount the owner was shown, which must match what is left: paid, less refunds already made in the dashboard, as Stripe says it now), audited before Stripe is asked, the amount sent explicitly, recorded from Stripe's answer or `charge.refunded`. A full refund made in the dashboard cancels the order (stock back once). A refund that fails later (`charge.refund.updated` with status `failed`, or `refund.failed`) puts the order back to paid, audited, with a note and an email to the owner.
- **Bookings racing a refund:** a courier booking that comes back after the order was cancelled, or its card payment refunded or unpaid, is kept (its AWB is needed to cancel the pickup) but the order is not moved; it is flagged, audited (`order.booking_exception`) and the owner alerted.
- **Logs:** fields named like `code` are redacted (SMS codes); Stripe's error code is logged as `stripeCode`, so a failed payment can be understood.
- **Keys.** Publishable key (public), secret key and webhook signing secret (write-only like every other key: blank in every answer, never in settings history, blanked in backups, redacted from logs together with `pi_…_secret_…` client secrets). Calls go to Stripe's fixed API through the official `stripe` library; the owner can't choose an address. `BUH_TEST_STRIPE_API` (tests only) accepts nothing but a plain-http loopback address.
- **Headers.** The CSP adds Stripe's documented hosts (`js.stripe.com` and `*.js.stripe.com` scripts and frames, `hooks.stripe.com` frames for 3-D Secure, `api.stripe.com` connections); `Permissions-Policy: payment=(self "https://js.stripe.com" "https://pay.google.com")` lets only Stripe's frame (and Google Pay's sheet) use the browser's payment sheet.

## Outbound calls (SSRF)

URLs an admin can type (SMS webhook, Infobip base URL) must be https, use port 443, carry no credentials, and resolve only to public addresses.

- **IPv4:** loopback, private, link-local (cloud metadata), CGNAT, reserved and multicast ranges are refused.
- **IPv6:** only global unicast is allowed, without 6to4, Teredo or documentation ranges. IPv4-mapped forms are judged by the IPv4 address inside them.
- **No DNS rebinding:** the address check runs inside the connection's own DNS lookup, so the address checked is the address connected to.
- **Every call:** redirects are not followed, there is a timeout, and replies are read only up to a size cap.

Carrier endpoints are fixed in code.

**Anthropic (AI writing).** "Write from photo" (`POST /api/admin/products/describe`) and Settings → AI writing → Test (`POST /api/admin/ai/test`) call one fixed address, `https://api.anthropic.com/v1/messages`, through `safeFetch` (https, no redirects, public addresses only, 60-second deadline, 256 KB reply cap). Nothing a person types changes where it goes.

- **Admin only:** both routes are behind the door, `requireAdmin` (same-site, signed in) and an allow-list of body fields; the describe body is capped at 9 MB and the photo must be PNG, JPEG or WebP by its real bytes (at most 3.5 MB), a stored product photo by its exact name, or an https address (sent to Anthropic as a link, never fetched by the shop).
- **The key (`ai.anthropicApiKey`)** is a write-only setting: reads return it blank with "saved" and its last 4 characters; it is blanked in settings history and in every backup, sent only in the `x-api-key` header, and never in a reply or a log (`logEvent` also masks any `sk-ant-…`). Anthropic's error messages are passed on with any key removed.
- **Answers are data, not markup:** every field is checked on the server (JSON only, lengths cut, markup, emoji and control characters removed, the weave matched to the shop's list, at most 4 colours with valid swatches); a reply that isn't the JSON asked for is refused with a clear message. Nothing is saved: the editor shows suggestions for the owner to accept.
- **Limits and audit:** 20 descriptions an hour per admin (10 tests per 10 minutes); each description is in the audit log (model, kind of photo, size; no image data).
- **Tests only:** `BUH_TEST_ANTHROPIC_API` points the calls at a stand-in, and only at a plain-http loopback address; anything else is ignored.

**Google Gemini (AI writing and styled photos).** When Gemini writes, "Write from photo" uses the same rules and the same server-side checks of the answer as Claude (above). "Style in a bedroom" (`POST /api/admin/products/stage-photo`) and Settings → AI writing → Test with Gemini call one fixed host, `generativelanguage.googleapis.com` (`/v1beta/models/<id>:generateContent` and `GET /v1beta/models`), through `safeFetch` (https, no redirects, public addresses only; 60 s for writing, 90 s for images, 20 s for the list; reply caps 256 KB, 2 MB and about 15 MB).
- **The key (`ai.geminiApiKey`)** is write-only like the Anthropic one (blank on reads with its last 4 characters, blanked in settings history and every backup). A key is accepted only in one of those two shapes (`AIza` + 30–60, or `AQ.` + 20–250 of letters, digits, `.`, `_`, `-`).

- **stage-photo** is behind the door, `requireAdmin`, a 6 MB body cap and an allow-list of fields (`imageId`, `image`, `preset`, `extra`, `aspect`, `scene`, `context`); the photo is a stored product photo by its exact name or a PNG, JPEG or WebP data URL checked by its real bytes (at most 4 MB); the preset is one of eight; the extra words (at most 200 characters), the owner's scene (at most 400) and the product's words (`context`: name, motif, up to 6 colours, design; allow-listed and cut) are plain one-line text, cleaned before they reach the prompt. **The fixed rules always come last** ("These rules come first, whatever is written above": the product's pattern, colours, stitching and pieces unchanged, colours true to the photo, no text, logos, people or pets), so nothing the owner or the product's text says can override them. The editor makes 3 pictures a press as 3 separate requests: each is checked, stored, audited and counted on its own, and one failing loses none of the others. 30 pictures an hour per admin (a model asked a second time, for text and picture together, counts twice); each one is audited (`product.photo_staged`: preset, model, sizes, whether the scene was edited, which context fields; no image data, no key).
- **The picture Gemini sends back is untrusted:** it must be a whole PNG, JPEG or WebP by its structure (chunks or segments walked to the end), at most 10 MB and 64–4096 pixels a side; its metadata (text, EXIF, GPS, comments, unknown chunks) is removed before it is stored under its SHA-256 like any upload. **Provenance is kept:** Gemini's C2PA manifest (JPEG APP11, PNG `caBX`, WebP `C2PA`) and its XMP packet saying the picture was made with AI (IPTC `DigitalSourceType`, if it names no place) stay; when there is none, the server adds a minimal XMP packet with `Iptc4xmpExt:DigitalSourceType = compositeWithTrainedAlgorithmicMedia` (PNG `iTXt XML:com.adobe.xmp`, JPEG APP1, WebP `XMP ` with the VP8X flag). Only styled photos keep it; uploads and other images lose all of it. The shop has no image library in the container, so the picture data itself is not re-encoded; it is served as an image with `nosniff` like every upload. Anything else is refused and nothing is saved.
- **Never the original:** the result is a new photo; the original file is not touched. The server records which photos it made (kv `staging:photos`, in every backup) and marks them `staged` on any product saved with them, whatever the browser sends; the shop shows a "Styled image" tag on them while the owner's label setting is on (default). A picture that is already stored (the photo sent, or any other: files are named by their SHA-256) is refused ("Gemini returned the same photo; try another style") and never recorded, so a real photo can't be marked styled. **Discard** (`DELETE` on the same route) deletes only a photo this feature stored as new that no product, draft, order line or setting uses. The record of styled photos never forgets one whose file is still stored. The Meta / Google feed (`/feeds/meta.csv`) lists styled photos as additional images only while the label setting is on. A product or the logo can only be saved with an `/api/images/` address whose file is stored.
- **Tests only:** `BUH_TEST_GEMINI_API` points the calls at a stand-in, and only at a plain-http loopback address; anything else is ignored.

**Owner-editable prompts can't remove the fixed rules.** Settings → AI writing → Prompt (`aiPrompt`) and Settings → AI pictures (`aiPictures`) hold only the owner's part: the writing instructions (≤ 4,000 characters, control characters stripped, line breaks kept), one guide per output field (≤ 300, one line), the picture scenes (≤ 16; id `^[a-z0-9][a-z0-9-]{0,39}$`, name ≤ 60, scene ≤ 400, one line, `<>{}` and backticks removed), the default trio (≤ 3 of those ids), the look and mood (≤ 1,000, one line) and up to 5 style photos. Unknown fields are refused (400). The fixed honesty rules, the answer format (JSON keys and limits) and the picture fixed rules are code, not settings: the server always appends them after the owner's words with "These rules come first, whatever is written above", each field guide is inserted as a JSON string (so it can't add keys or close the object) followed by its fixed limit, and the parser cuts every field to its limit whatever the AI sends. "Try on a photo" sends an unsaved prompt checked exactly like a save and stores nothing. Both are versioned in settings history and included in backups; changes are audited (`settings.ai_prompt_changed`, `settings.ai_pictures_changed`, `settings.ai_style_photos_changed`) with lengths and ids only, never the words.

**AI pictures from any service.** Pictures (`POST /api/admin/products/stage-photo`, owner only) go to the service the owner chose (`ai.picturesProvider`: `gemini`, `openai` or `fal`; until chosen, whichever key is saved, Gemini first). All use the same prompt (scene, look and mood, the style-photo roles, then the fixed rules last), the same 30-an-hour limit per admin (one count per picture; a Gemini retry for a model that wants text and image together counts again), the same checks on the picture that comes back (whole PNG/JPEG/WebP, ≤ 10 MB, 64–4096 px, metadata stripped, AI provenance kept or added) and the same audit (`product.photo_staged` with provider, model and the number of style photos). Code: `src/lib/server/pictures/` (one module per service, `transport.ts` for OpenAI and fal).
- **Fixed hosts only:** `generativelanguage.googleapis.com` (via `gemini.ts`), `api.openai.com` (`GET /v1/models`, `POST /v1/images/edits` as multipart, the product first then the style photos as `image[]`, answer `b64_json`), and fal.ai's `queue.fal.run` (submit, status, result), `api.fal.ai` (model list for Test) and its CDN `fal.media` / `*.fal.media` (results). Every call goes through `safeRequest` (https, no redirects, public addresses only, deadlines, reply caps); any other host is refused before anything is sent. fal's `status_url` / `response_url` are used only when they are on `queue.fal.run`; a result address off fal's CDN is refused and never fetched (results are asked for as data URIs with `sync_mode`; a CDN download carries no key). fal model ids must match `^(?!.*//)(?!.*\.\.)[a-z0-9-]+/[a-z0-9.-]+(/[a-z0-9.-]+){0,4}$`; OpenAI image models `^(gpt-image|chatgpt-image)[a-z0-9.-]{0,60}$`.
- **Keys (`ai.openaiApiKey`, `ai.falApiKey`)** are write-only like the others (blank on reads with their last 4 characters, blanked in settings history and every backup), accepted only in their shapes (`sk-…`, `sk-proj-…`; fal `key-id:key-secret`), sent only in `Authorization: Bearer` (OpenAI) or `Authorization: Key` (fal), and `logEvent` masks `sk-proj-…`, `sk-svcacct-…`, `sk-admin-…` and fal-shaped keys. Providers' error messages are passed on with keys removed; 401/403, no credit, 429, safety refusals and timeouts become plain messages.
- **Style photos** (`POST /api/admin/ai/style-photo`, owner only, body ≤ 2.1 MB): PNG, JPEG or WebP by their bytes, ≤ 1.5 MB and ≤ 2,048 px (the hub shrinks them to about 1,024 px first), metadata (EXIF, GPS, text) removed, stored by SHA-256 in the images folder (so in every backup). The `aiPictures.references` list (≤ 5) accepts only stored pictures that pass the same checks, and they are re-checked (metadata stripped) before each request. They are sent only when switched on, there are some, and the scene isn't set to its description only.
- **Angles.** Numbered angles in the owner's look and mood (`splitAngles`, src/lib/staging.ts) are never sent as a list: each picture is its own request with `angle` (1–4, only an angle that is in the saved prompt) and, after the first, `sameRoom` (only a picture this feature made, checked against the styled-photo records, and only sent when the owner switched on "Keep exactly the same room"; otherwise ignored) as the second image. The fixed rules (now also "one single photograph, never a collage") still come last. The look is at most 3,000 characters, one line, cleaned as before.
- **Quick add** (`GET/POST/DELETE /api/admin/products/quick`, src/lib/server/autoAdd.ts): owner only behind the door, body ≤ 8 KB, an allow-list (`key`, `photos`, `price`, `compareAtPrice`, `category`, `sizes`, `title`, `publish`). Photos must be stored images by exact name; sizes are the catalogue's presets; the product goes through `createProduct`'s normal checks, saved hidden, with no fabric or thread count invented. A request key makes a double tap add one product. The background work (writing, pictures, publishing) uses the same functions, limits (20 descriptions and 30 pictures an hour per admin) and audits as the hub's buttons, plus `product.quick_added` and `product.quick_finished`. The jobs are in the database (kv `autoai:jobs`, in every backup); a lease (kv `autoai:lease`, renewed with every step, taken in one immediate transaction) lets one copy of the shop work at a time during an update's overlap, and pictures already made are kept, so none is paid for twice. A "wait" from the service is waited out (at most 6 times, at most an hour each). The placeholder name's SKU is replaced once, when the AI names the still-hidden product; after that SKUs are never rewritten.
- **Inventory → Make pictures** adds pictures to an existing product with `POST /api/admin/products/<id>/styled-photos` (owner only, body ≤ 2 KB, `{ urls }` only): only photos this feature made, first with the owner's photo last (or after their source photo, as set in Settings → AI pictures), once (sending twice adds nothing), at most 8 photos; saved through `updateProduct` (validated, audited before it is saved) and audited as `product.photo_staged_added`.
- **Tests only:** `BUH_TEST_OPENAI_API` and `BUH_TEST_FAL_API` point those calls at a stand-in, only at a plain-http loopback address and only in a test server.

**DeepSeek (AI writing).** When DeepSeek writes, "Write from photo" uses the same rules and the same server-side checks of the answer as Claude (above). It and Settings → AI writing → Test with DeepSeek call one fixed host, `api.deepseek.com` (`POST /chat/completions` and `GET /models`), through `safeFetch` (https, no redirects, public addresses only; 60 s for writing, 20 s for the list; reply caps 256 KB). DeepSeek makes no pictures: styling stays Gemini only.

Gift lines are stored on the product (`giftLines`, in its JSON, so every backup and restore carries them) by festival id from the shop's own catalogue or `everyday`, each at most 160 characters with markup removed; anything else is refused on save. The festival a line is written for is worked out on the server from the storefront's own theme pick (the admin's override and switched-off festivals applied; days of remembrance never get one); a festival the browser names must be one the calendar offers then. - **Weave rename** (`POST /api/admin/catalog/weaves`, admin only, 2 KB body): changes the weave on every product, every editor draft and the list in one transaction, audited (`catalog.weave_renamed`) before it commits; if the audit log can't be written nothing changes (503). Removing a weave products still use is refused.

## Couriers

- Live bookings use the carrier's own AWB. If the carrier is down or refuses, the booking fails visibly. Older builds invented a random AWB and marked the order booked, and checkout gave every new order a made-up AWB and tracking link.
- **Jeebly's API, verified:** the Scheduled API (create, label, track, cancel) was checked against Jeebly's docs and its demo system with the owner's demo keys (2026-10-19). Hosts, paths, header names (`X-API-KEY`, `client_key`) and reply fields are in one module, `src/lib/jeeblyApi.ts`. `success` is a string; anything but `"true"` is a failure.
- **Nothing invented:** no AWB, label, link or sender detail is made up. The AWB is Jeebly's `"AWB No"`; Jeebly gives no tracking link, so none is stored. The sender is the owner's own pickup details; a booking is refused (listing what is missing) until Jeebly's required pickup fields are filled in. A parcel's weight comes from the sizes' weights copied onto the order when it was placed; with a size unweighed, a booking that reaches Jeebly needs the weight typed in (`400 weight_required`), never a default.
- **Outbound calls:** every Jeebly call (live and sandbox) goes through `safeRequest` (src/lib/server/outbound.ts): https only, public addresses only, checked when connecting, no redirects, a time limit for the whole reply, and JSON replies read up to 256 KB.
- **Live address:** Jeebly's production host is a setting, accepted only as `https://` on `jeebly.com` or a `*.jeebly.com` host (no credentials, port, path), checked on the server. The live keys follow it: moving it to another host drops them unless typed again.
- **Test mode:** a sandbox booking uses separate sandbox keys on Jeebly's demo host; a failure records nothing. With no keys, an offline practice booking (`PRACTICE-…`) is made and nothing is sent. Both need the owner's explicit yes (`testBooking: true`, else `409 test_booking`), are marked `simulated` and are never shown to customers. A booking remembers its environment (`carrierEnv`), so its label, tracking and cancel go to the same host with the same keys.
- **Live mode gate:** switching Jeebly Live on (any settings save, including autosave and restoring history) is refused without the live address (`409 live_base_required`), and unless a Sandbox check passed in the last 30 days (`409 sandbox_check_required`). The only way past the check is `POST /api/courier/live` with the exact typed phrase, audited (`courier.live_override`) before the setting changes.
- **Sandbox check** (`POST /api/courier/sandbox-check`, `requireAdmin`, empty allow-listed body, 20 an hour): a PREPAID dummy order marked TEST on the demo host with the saved sandbox keys: create, label, track, cancel. The result is kept in the database (`kv`, so in backups) and audited (`courier.sandbox_check`) before it counts. `scripts/jeebly-sandbox-check.mjs` runs the same steps from a checkout, with keys from the environment only, printing status codes and Jeebly's message text, never the keys.
- **Carrier label** (`GET /api/admin/orders/<id>/carrier-label`): `requireAdmin`, 60 an hour per admin; the PDF is fetched from Jeebly with the keys on the server and passed on only if it says `application/pdf`, starts with `%PDF-` and is at most 2 MB (reading stops just past it); not cached; `no-store`, `nosniff` and `default-src 'none'` (no CSP `sandbox`, which stops Chrome's PDF viewer); the file is named by the AWB only when it matches `[A-Za-z0-9-]{4,40}`; audited (`courier.label_printed`) before it is sent.
- **Tracking:** `GET /api/admin/orders/<id>/carrier-tracking` (`requireAdmin`, 120 an hour) asks Jeebly again; Track Order shows a real booking's status and events from a 5-minute cache per AWB (a failed lookup is kept 30 seconds), with at most 60 calls a minute to Jeebly for customers and a separate 60 for the owner's refresh. Phones and emails in Jeebly's description and hub text are masked before customers see them. Only status, description, hub and time are kept: Jeebly's phones, rider, proof-of-delivery and signature fields are dropped on the server. Tracking never changes an order's status.
- **Cancelling:** cancelling an order (or Cancel & refund) with a Jeebly booking calls Jeebly's cancel; the answer is audited (`courier.cancel`) before it is reported. A refusal is never reported as cancelled: the owner is told to cancel it in the portal and the order is flagged. A full refund in Stripe's dashboard (its webhook) and a booking that comes back after the order was cancelled cancel with Jeebly the same way, as `stripe` or the booking admin. An unanswered booking can't be cancelled through the API: the order is flagged to check the portal. Only one cancel per order is sent, and none once the carrier says cancelled.
- **Eco Express** has no real booking connection (its published spec points at an Apiary mock): live booking is refused with a clear message and nothing, keys included, is sent to the mock.
- **Test connection** tracks a made-up reference (it creates nothing) and reports the carrier's HTTP status and its `message` (text only, 200 characters, the keys themselves and phones/emails masked). It never calls keys valid unless the carrier's reply says success.
- **Never booked twice:** each live booking is recorded on the order in the database. A repeat request (with or without `rebook`) returns the AWB already issued, and a test booking never replaces a real one. If the carrier never answered an attempt (also a 2xx it could not read, a reply cut off, or any 5xx), it may or may not exist: the owner must check the carrier portal and confirm before booking again, in any mode; a test booking never clears it.
- **Enter tracking number** (`POST /api/admin/orders/<id>/tracking`): `requireAdmin` (door, session, same site), a 2 KB body with allow-listed fields (`carrier`: `jeebly`, `echo` or `other` with a 2–40 letter `carrierName`; `awb`: 4–40 of `[A-Za-z0-9-]`; optional `trackingUrl`, https on a public host via `assertPublicHttpsUrl`; `replace`). Only for confirmed, dispatched or out-for-delivery orders. Audited (`order.tracking_entered`, or `order.tracking_replaced`) in the same transaction, so it is never saved or reported done without it. A real booking already on the order is replaced only with `replace: true` (`409 tracking_replace` first). Customers see the courier's name only with a link the owner typed.
- One booking per order at a time.
- Inputs are allow-listed and length-capped.
- Every dispatch, test, Sandbox check and Live switch is audited.

## Requests and errors

- Bodies are size-capped per route (2 KB for codes, 256 KB for dispatch, 9 MB for the photo studio) and must be JSON objects.
- Image uploads must really be PNG, JPEG or WebP (checked by magic bytes); SVG is refused.
- Unexpected errors return a generic message. The details go to the server log, with secrets redacted and phones/emails masked.

## Audit log

`DATA_DIR/audit-YYYY-MM.jsonl` records every action that moves money, stock or the shop's state: orders placed and changed by the owner (status, payment status, notes, with before → after), card payments started, paid, declined, cancelled and refunded (in full or in part, from Stripe's word), bank transfers uploaded and checked, WhatsApp confirmations, courier bookings and tests, stock moves (who, reason, old → new), products created, changed (price and sizes' charges before → after), duplicated, archived, reordered, drafts discarded, settings saved and restored (and the financial year's start), the admin link, sign-ins and refusals, sign-outs, password changes and resets, passkeys and recovery codes, backups taken, failed and restored, updates and rollbacks asked for, SMS and email tests, monitor alerts, expenses and their bills, and every export (the accountant's ZIP, the audit CSV/JSONL). Each line carries an HMAC over the previous line, so editing, deleting or reordering a line is detected (`verifyAuditLog`). Each line also names its key id (`kid`: 16 hex characters of SHA-256 over the HMAC key, which can't be turned back into the key), and the first line of a month records the previous month's last sequence number and MAC (`prevMonth`), so a missing month, or one cut short at its end, is reported.

- **Audited before it counts:** order changes, payments, refunds, bank checks, stock moves, price changes, expenses, bills and exports are written to the log inside their transaction (or before the export is built); if the log can't be written, nothing is saved or sent (503).
- **The viewer** (Money → Audit log, `GET /api/admin/audit`) is read-only, signed-in only, and checks every month's chain, per key segment: it names the file and line where it breaks. The key never leaves the server; `restore-backup.mjs` keeps the server's own (`--replace`) or copies the running shop's (`DATA_DIR`) into a new folder. On a new server the first new entry starts a fresh segment (`prev: "genesis"`, `after`: the last restored MAC) instead of chaining onto MACs it can't check.
- **What each status means:** entries naming this server's key id must verify, or the month is BROKEN (red). Entries naming another well-formed key id, with every link in order, are "signed by another server's key (fingerprint …): restored from a backup" (neutral). Entries with no key id (written before key ids) are checked with this server's key; if none verify they are "unverified" (amber), as are entries naming a malformed key id; some verifying and some not is BROKEN. A key change inside a chain (not at a fresh segment), a fresh segment under the same key, or a month link that doesn't match is BROKEN. Limitation: a whole month rewritten under a made-up key id reads as restored; the month links around it, the backups and the server's own copy are the cross-check.
- **Reading it:** each file is read a piece at a time; the list of actions and each month's check are kept until the file's size or time changes. The CSV/JSONL exports are streamed, one export at a time (429), and an export that fails is itself audited (`audit.export_failed`, `report.export_failed`).
- Not audited on purpose: what a customer does before an order exists (browsing, SMS codes beyond the global limit, opening WhatsApp), product drafts saved as the owner types (the published change is), and reads.

- Who acted (`by`: the admin's sign-in email, or `stripe`, `customer`…) and the order number (`orderId`) are kept exactly: the file is the owner's own record (0600, and only in encrypted backups). Everything else is redacted as in the server log: secrets by field name, customers' phones and emails in free text masked. Order numbers and dates are never mistaken for phone numbers (digits inside an identifier are left alone), in the audit or the server log.
- A change audited inside its transaction whose save then fails (a full disk, a busy database) gets an `audit.rolled_back` line straight after, so the log never claims a change the database doesn't have.

## Expenses, bills and the accountant's export (BUH-02.10)

- **Routes** (`/api/admin/expenses…`, `/api/admin/reports…`, `/api/admin/audit…`): the door and a session (`requireAdmin`), same-site for every change and for the downloads, size-capped JSON bodies (8 KB; a bill 10 MB as base64), allow-listed fields, `handleRouteError`.
- **Money in fils:** amounts are parsed from the text the owner typed into whole fils (no floating point), 0.01 to AED 10,000,000. Categories and payment methods come from server-side lists.
- **Never overwritten:** every state of an expense is a row in `expense_versions`; "Remove" marks it (who, when, why); a bill taken off keeps its file. Edits must name the version the owner saw (409 otherwise).
- **Bills** are checked by their bytes (JPEG, PNG, WebP, HEIC or PDF; SVG, HTML and anything else refused, whatever the browser called it), 10 MB each, 20 per expense. Photos are re-encoded in the browser (2000 px JPEG) and the server strips EXIF/GPS, XMP, IPTC, comments and PNG text chunks again; HEIC (no safe decoder here) and PDFs are stored as they are. JPEG also loses APP2's MPF (the extra pictures; the colour profile stays) and anything after the end-of-image marker (scan by scan). Files live in `DATA_DIR/expenses/` (0600) under random names, refused (507) with under 1 GB free or 2 GB of bills; the same bytes again on one expense (by SHA-256) return the bill already there. The file is renamed into place inside the database transaction, before COMMIT (removed again if the commit fails), so a row never lacks its file. They are served only to the signed-in hub: the content type fixed by the kind (one of five extensions, checked on every read; never the stored type), `nosniff`, `no-store`; photos `inline` under `default-src 'none'; img-src 'self'; frame-ancestors 'none'; sandbox` (set for that path in `next.config.ts` and by the route); PDFs as `attachment` (browsers won't render a PDF under a sandbox policy, and a PDF can carry script). Category and file names are NFKC-normalised, stripped of invisible format characters (`\p{Cf}`) and single-spaced; categories are compared that way (case-insensitive) for duplicates. An expense's note keeps up to 2,000 characters in the audit log (masked as usual; other strings 500).
- **The ZIP** is built on the server's disk one file at a time and asynchronously (bills copied in pieces, the expenses and the audit log streamed and deflated as they are made), only when the disk keeps 1 GB free after its estimated size (507 otherwise), one export at a time for the whole shop (429; the lock is freed when the download ends, or after 15 minutes), in `DATA_DIR/exports/` (never in backups, removed once sent or after an hour). A build that fails after its `report.exported` entry gets a `report.export_failed` one. It and holds only what the accountant needs: customer name and emirate (no phones, emails or addresses), amounts, payment references, the period's audit lines (already redacted) and the chain check. CSVs are UTF-8 with a BOM and formula-safe. Who exported which period is audited first.
- **Refunds** are booked from the refunds ledger (`card_refunds`: one row per refund with its amount, time, source `stripe`|`hub` and Stripe refund id, unique per direction; a refund that failed is a negative row), written in the same transaction as every change to an order's refunded amount. Reports sum it by the day of each row, never the order's date. Orders refunded before it are filled in once (`backfillRefundLedger`, idempotent, at start and every minute, and before a report) with the refund time or the order's last change, marked approximate in `refunds.csv`.
- **Totals** of expenses are summed by the database (all of them); the ZIP and the backups read expenses a page at a time.
- **Backups** include the expense tables, the refunds ledger, `expenses.csv`, `expense_bills.csv` and every bill; the restore script accepts only bills named `<24 hex>.<jpg|png|webp|heic|pdf>` and refuses a backup whose bill rows name anything else, and says if a bill is missing.

## UAE VAT and tax invoices (BUH-02.17)

- Off by default. Turning it on is owner-only, needs a 15-digit TRN, a start date not in the past and the typed confirmation `TURN ON VAT`, and is audited before it counts. While on, the TRN and the date can't change.
- An order's VAT is worked out on the server in fils when it is placed (never from the browser) and stored once (`order_vat`); orders from before the date are never rewritten. Invoice and credit-note numbers are taken as `MAX(seq) + 1` inside an IMMEDIATE transaction: no gaps or doubles, also with two copies of the shop.
- The customer's receipt/tax invoice is at `/invoice/<order>.<HMAC>` (made from the server's key, not stored, not guessable from an order number; limited per address; an unknown one is the ordinary 404). It and the hub's copy are plain HTML with no scripts, `default-src 'none'; style-src 'unsafe-inline'`, `no-store`, `noindex` and no referrer.
- New data (`staff_accounts`, `order_vat`, `vat_invoices`, `vat_credit_notes`, expenses' `vat_fils`/`supplier_trn`, the VAT settings) lives in `shop.db`, so backups and the restore carry it (`test/vat.test.mts` restores it).
- The `vat.invoice_issued` and `vat.credit_note_issued` audit entries are written once the transaction that took the number has committed (`afterCommit` in db.ts): a rolled-back number is never in the log. A card payment is invoiced only when Stripe said it was live (`card_livemode = 1`); an unknown mode is not.
- Documents are brought in line once per VAT return (JSON or CSV), and only for orders not yet final (no invoice yet, or credit notes that don't match the refunds or the cancel); the customer's invoice page reads its own order and takes the write lock only when something is due.
- **Credit notes cover:** a cancelled invoiced order (in full), and card refunds in the refunds ledger (partial or full, from the hub or the Stripe dashboard, and a refund that failed afterwards). **They don't cover:** money given back outside the shop for a cash-on-delivery or bank-transfer order (the shop has no record of such a refund, so nothing to credit: cancel the order for a full credit, or have your accountant issue a manual credit note), and card **chargebacks/disputes** (Stripe's dispute events are not read). Both are for the accountant to handle by hand.
- Reports with VAT orders also show sales and profit without VAT (output VAT taken off the sales and the refunds, input VAT off the expenses) beside the figures with VAT, which are labelled so; sales.csv adds `vat_aed` and `total_excl_vat_aed` (the gross `total_aed` stays).
- "Prices exclude VAT" is a choice with a warning in the settings: UAE consumer prices are normally shown with VAT, so inclusive stays the default.

## Headers

Every page sends:

- **Content Security Policy:** scripts and connections only to this site, no plugins, no `<base>`, no framing. Workers only from this site (`worker-src 'self' blob:`: the service worker, and the order confirmation's confetti, drawn in a worker from a `blob:` URL) and the app manifest only from this site (`manifest-src 'self'`).
  - Fonts (Cormorant Garamond and Inter, SIL Open Font License) are files of the shop itself (`src/app/fonts/`, served under `/_next/static/`), so `font-src 'self'` stays: no font host sees visitors.
  - Exception, for Firebase phone sign-in: reCAPTCHA scripts and frames (`www.google.com/recaptcha/`, `www.gstatic.com/recaptcha/`, `recaptcha.google.com/recaptcha/`), `apis.google.com`, frames from `*.firebaseapp.com`, and connections to `identitytoolkit.googleapis.com` and `securetoken.googleapis.com`.
  - **Trade-off:** the policy is fixed at build time (a per-request one costs too much, below), so these Google hosts are allowed even while Firebase is off. They are Google-run, path-limited where CSP allows, and nothing on the page loads from them unless Firebase is switched on. A custom auth domain (not `<project>.firebaseapp.com`) is not covered; keep the default.
- `X-Frame-Options: DENY`, `nosniff`, `Cross-Origin-Opener-Policy: same-origin`, HSTS, and a `Permissions-Policy` that allows only geolocation (for the address pin).
- API responses add `Cache-Control: no-store`.

**Why there is no nonce CSP.** A per-request nonce would also block injected inline scripts, but it renders every page per request. On this shop the storefront fell from ~790 to ~145 requests/s, and even an idle proxy cost ~35%. React escapes all rendered text and there are no raw-HTML sinks, so the static policy is the better trade.

## The installed app (service worker)

The shop installs as an app (manifest at `/manifest.webmanifest`, icons at `/icons/…`). A small hand-written service worker, `/sw.js` (source: `src/lib/serviceWorker.ts`, no library), controls the whole site (scope `/`).

**What it keeps on the phone** (the browser's Cache Storage for this site):

| Cache | What | Why it is safe |
| --- | --- | --- |
| `buh-shell-<version>` | the offline page (`/offline`), the manifest and the app icons | public, the same for everyone |
| `buh-static-<version>` | the shop's own scripts, styles and fonts (`/_next/static/…`), at most 300 | public, named by their content: a file never changes under the same name |
| `buh-images` | uploaded product photos and the logo (`/api/images/…`), the latest 120 | public, named by their content (SHA-256) |

**What it never touches** (the request goes to the server as if there were no worker, and nothing is stored):

- anything that is not a `GET`: orders, checkout, phone codes, sign-in, every admin change;
- every other `/api/` address: products, prices and stock, orders and order tracking, the chat, settings, live updates (`/api/events`), and every admin address;
- other sites (Unsplash photos, Google reCAPTCHA);
- pages (`/`, `/p/…`): always fetched from the server while online and never stored, so a new version shows at once and the zero-downtime version switch works exactly as before. Only when the phone is offline does a page request get the stored offline page;
- every other page (the Admin Hub's private link among them): not answered at all; and any file requested without a referrer (the hub's own scripts and styles, sent with `Referrer-Policy: no-referrer`).

The worker never stores a response marked `no-store` or `private`, nor one from another site. All API answers carry `Cache-Control: no-store` anyway.

**Updates:** `/sw.js` is sent with `Cache-Control: no-cache` and contains the release's version, so every release is a new worker. It installs in the background and **waits**; the page shows **New version ready — Refresh**, which tells it to take over (`SKIP_WAITING`) and reloads; otherwise it takes over when the app is next opened. On taking over it deletes the previous version's caches. A shopper's page that is in the background switches by itself, never with a product, the bag or checkout open (as before).

**Kill switch (never stranded on a phone):**

- The worker asks the server for `/sw.js` when it takes over and then at most every 10 minutes while pages are opened (also after the browser restarts it, which phones do often). A **404** (the shop was rolled back to a version from before the app, BUH-02.05.00 or older, which has no `/sw.js`) or the **reset** answer (below) makes it delete its caches and unregister. A 502/503 during an update, or no network, is not a 404 and changes nothing.
- The page does the same when registering fails because `/sw.js` is a 404.
- **`SW_RESET=true`** (a server setting, for emergencies such as a broken worker): `/sw.js` becomes a reset worker that takes over at once (no waiting for tabs to close), deletes the caches, unregisters and answers nothing. Every phone that opens the shop is cleaned on that visit. While it is on, **`/reset-app`** answers with `Clear-Site-Data: "cache", "storage"`, the browser's own wipe of this site's caches, workers and storage (it also empties that phone's bag and saved delivery details; sign-in cookies are kept). It is a 404 while `SW_RESET` is off, so nobody can wipe a shopper's bag with a link.
- **Rolling back to a version from before the app:** the shop works as a website straight away (pages always come from the server). Each phone's leftover worker removes itself the next time the shop is opened after the worker restarts, usually the same visit, at most about 10 minutes later. Nothing it kept is needed to place or find an order.

**Navigation preload** is off: a page address the worker leaves alone (an `/api/` address opened directly, `/sw.js`, `/reset-app`) would otherwise be fetched twice.

**Icons** are drawn once per logo and size, and requests that arrive while one is drawn wait for it. A logo larger than 4096 px on a side is refused when saved (the size is read from the PNG/JPEG/WebP header) and is never drawn (the letters are), so a small file that claims a huge size cannot exhaust the server.

**Removing it by hand:** the browser's site settings → Clear data removes the worker and its caches.

Tested by `test/sw-source.test.mts` (every rule above, the 404 and reset kill switch, the 10-minute re-check, preload off), `test/app-icons.test.mts` (one drawing for many requests, the logo size limit) and `test/browser-app.test.mts` (in Chromium: registers for `/`, API and admin responses never come from the worker, nothing under `/api/` but photos is stored, the offline page with the server down, and `SW_RESET=true` removing the worker and its caches on the next open).

## Deployment

- **Docker:** non-root, `read_only`, `tmpfs /tmp`, `cap_drop: ALL`, `no-new-privileges`, bound to `127.0.0.1`, data in a volume, healthcheck on `/api/health`.
- **Two copies, one serving.** `app-blue` and `app-green` share one definition (same image, settings, volume and hardening). Caddy health-checks both every 2 s and sends traffic to the first healthy one; both run only for the minute of an update, on the same SQLite database (WAL mode, one host: safe for two processes).
- **The updater is opt-in and powerful.** It is off unless the owner enables the compose profile `autoupdate`. It mounts the Docker socket, which gives it root-equivalent control of the host: whoever controls the updater controls the server. That is acceptable because it:
  - runs no network listener and talks only to the Docker socket and the registry (`ghcr.io`), plus the alert webhook if one is set (https only, 10 s timeout);
  - runs a fixed image (`docker:29.9.1-cli`, pinned by digest) and the script from this repository, mounted read-only; nothing it pulls is executed by it, only started as the shop;
  - reads only `UPDATE_CHECK_MINUTES` and `ALERT_WEBHOOK_URL` from `.env.production`, so the shop's secrets are not in its environment (it can still read the file: the project folder is mounted read-only, because `docker compose` needs it);
  - has a read-only root filesystem, `no-new-privileges`, and only the `CHOWN`, `DAC_OVERRIDE` and `FOWNER` capabilities (to write its alert log into the shop's volume for the shop's user).
  The protection that matters is the server's: SSH keys only, and nobody else with access to Docker on it.
- **Single-container mode (Podman, on Windows or a Linux server) is the same trade-off.** The one-line `setup` mounts Podman's API socket into the published updater image (`ghcr.io/cxsmtp/buh-updater`: the docker 29.9.1 CLI binary on `alpine:3.24`, without the CLI image's Compose and Buildx plugins or its SSH and source-control clients, plus `deploy/updater`, built and published from main like the shop), and the long-running updater keeps it. That gives it control of Podman, and so of every container and volume of that Podman user (rootless on a Windows Podman machine: the machine's user, not Windows itself; on a rootful Linux server: every container on the server, i.e. root-equivalent, as with Docker's socket). It runs `--read-only`, `--cap-drop ALL` plus only `CHOWN` and `FOWNER` (to take back its request and status folders: Podman's Docker API hands an empty volume to the user of the container that mounts it, the shop's), `no-new-privileges`, `--pids-limit 128`, no listener; `label=disable` only so that SELinux lets it use the socket. Its code is in the image; nothing on the host is read.
  - It updates itself from the same image name: the new updater must keep running and reach Podman before it takes over, otherwise it is removed and the image is not tried again. After the handover the old updater stays (idle) until the new one has finished a full round; if it does not within 10 minutes, the old one removes it, takes the name back, marks the image bad and raises an alert. Trusting the updater image is trusting GitHub Actions on this repository's main branch, as for the shop image.
  - **Private images.** The packages on ghcr.io are private. Podman logs in with a GitHub token (classic) that can only read packages (`read:packages`), kept in Podman's `auth.json` (mode 600; on a Linux server in `/root/.config/containers`, not the volatile `/run/user/0`). Podman's Docker API does not use that login for a pull the docker CLI asks for (tested with Podman 4.9 and 5.7), so the `setup` line mounts the folder read-only into the updater, which points the docker CLI at the file (a link in its own volume, never a copy); the token is never printed, logged or put in the status. Every download reads nothing from a terminal, and the updater image uses the docker CLI 28 (27 asked "Login prior to pull: Username:" when a registry refused, and waited for ever). A refused download (no login, expired token) is an alert (at most once an hour) and a note on Settings → Versions; it is retried at the next scheduled check only, and no image is marked bad for it.
  - **The images' supply chain.** Only a push to main (or a manual run on main) publishes, and only the publish jobs get `packages: write`; pull requests build and test with read-only access. Third-party actions are pinned by commit, base images (`node:24.22.0-alpine3.24`, `alpine:3.24.2`, `docker:29.9.1-cli`, `caddy:2.11.7-alpine`) by digest; the shop image has no npm, npx, corepack or yarn (it only runs `node`), the proxy image no curl, ShellCheck in CI by digest; Dependabot proposes newer pins as pull requests (`.github/dependabot.yml`). The updater and proxy images are reproducible (fixed timestamps, no per-commit labels), so an unchanged one keeps its image ID and is not restarted.
  - **A version is published once and never changes.** Each image is pushed by digest, then `deploy/ci/publish-version.sh` gives it its version tag: if `buh:<version>` (or the updater's or proxy's) already names other contents, the publish fails and no tag moves (`latest` included); a re-run of the same commit changes nothing. Each release then gets the git tag `v<version>` and a GitHub Release (private, like the repository) listing the three digests and its changelog entry; only that last job has `contents: write`.
  - **Integrity on the server (trust on first use).** The updater records the digest each version first came with, in its own volume, and every install (version, digest, time, and whether it was automatic, asked for, a switch back or the set-up); Settings → Versions shows the history and a "verified" mark when the installed digest is the recorded one. The same version number under another digest later is refused, with a critical alert and a warning on the page. The shop is started as `ghcr.io/cxsmtp/buh@sha256:…` (what runs is exactly what was checked; `podman ps` shows the digest), and switching back to a recorded version fetches it by that digest, never by its tag.
  - **What digest pinning does and does not protect against.** It protects against a moved or overwritten tag and against corrupted downloads: a version can no longer change under the shop. It does not protect against someone who can write to the registry publishing a *new* version number with bad contents: the updater would install that like any release. That risk is limited by who can write: keep package write access to this repository's Actions only. To check it: GitHub → your picture → Your profile → Packages → `buh` (then `buh-updater`, `buh-proxy`) → Package settings → **Manage Actions access**: only `cxsmtp/buh`, role Write; and under **Manage access** (or Collaborators), no other person or team with Write or Admin.
  - **Signing (optional, off).** Key-based Cosign signing (`cosign sign --key … --tlog-upload=false`, so nothing goes to the public transparency log) would let the updater check that an image was signed by this repository's key, which also covers a new version published by someone with registry write access but not the key. It is not built: it needs a private key that the owner creates and adds as a repository secret (`cosign generate-key-pair`, then Settings → Secrets and variables → Actions), and the public key on the server; nobody but the owner should handle the private key. Until then, the protection is the digest record above plus limited write access.
  - The HTTPS proxy (`ghcr.io/cxsmtp/buh-proxy`, Caddy 2.11.7) runs on the host network (it reaches the shop on `127.0.0.1`), as a non-root user, read-only, with every capability dropped except `NET_BIND_SERVICE` (ports 80 and 443) and `no-new-privileges`; its admin endpoint is off (on the host network it would be open to local users). It uses the same protections as the Compose Caddy (one shared file): the 12 MB body limit, `X-Real-IP` set from the connection (a visitor's own header is replaced), no `Server`/`X-Powered-By`, TLS 1.2 and newer (Caddy's defaults). HSTS and CSP come from the app and pass through once. The shop listens on `127.0.0.1` only and trusts `X-Real-IP` (`TRUST_PROXY=1`) because only the proxy can reach it.
  - The shop container is started only from a fixed definition: `--read-only`, `--tmpfs /tmp`, `--cap-drop ALL`, `no-new-privileges`, `--pids-limit 512`, the data volume, the request volume and the read-only status volume. The container name, port, volume names and extra `KEY=VALUE` settings come from the updater's environment and are checked strictly before anything runs (names `[A-Za-z0-9_.-]`, a port 1–65535, keys `[A-Z_][A-Z0-9_]*`, values without spaces, quotes or shell characters; `DATA_DIR`, `PORT`, `HOSTNAME`, `NODE_ENV` cannot be changed), and each is passed as its own argument, so no value can add a flag, a mount or a command.
  - It never moves the shop to other data: it refuses to touch a container whose `/data` is not the configured volume, and never starts a shop on a data volume that does not exist (only the first set-up of a new shop creates one).
  - The set-up carries the shop container's own settings over (its `-e` values, secrets included). They go to `docker run` as an env file in the updater's own volume (folder 700, file 600, root in the updater only), never on a command line, in the log, an alert or the status the shop reads; only their names are logged. Anything it cannot carry (another mount or port, a value with a line break) stops the set-up with a list, and nothing changes. `SHOP_ENV`, by contrast, is in the updater's environment: keep secrets out of it.
  - It never starts a second shop on the same data: nothing is started while another running container uses the data volume (the set-up also refuses a stopped one).
  - Requests are written whole to a temporary file and then linked into place (never replacing one), so the updater never reads a half-written request.
  - Requests and status work exactly as with Docker Compose ("Version switching from the Admin Hub", above): the shop can only drop one line into a sticky, non-listable folder and read the status. The set-up makes the updater (root in its container) the owner of both volumes before the shop mounts them.
- **Updates never skip the safety checks.** The database is snapshotted before a switch (no snapshot, no switch); a new version must pass its health check and render the home page before it gets traffic from the old one; a version that fails is removed, remembered and not retried. Alerts go to the updater's own volume (`/state/alerts/alerts.log`; the updater has no access to the shop's data volume and no Linux capabilities) and, optionally, the webhook. Versions before 2.0.0 cannot be rolled back to on a 2.0 database (stock is per size); the updater refuses them. No secrets are written to either.
- **Database changes must be additive.** During a switch the old version runs against the new version's database, and a rollback runs it there for good: migrations add tables or columns, never drop or rename.
- **Published image** (`ghcr.io/cxsmtp/buh`): built by GitHub Actions from main only, after a smoke test that starts it read-only, as user 1001, with every capability dropped. Pull requests build and test it but never publish. No secrets are baked in: the support email and shop address are read from the environment at start-up.
- **PM2:** one instance. Codes and limits live in process memory; move them to Redis (or the database) before running more. For the same reason, an SMS code sent in the minute of a blue/green switch may have to be requested again.
- **`TRUST_PROXY=1`** only behind nginx, which sets `X-Real-IP`. Without a trusted proxy, per-address limits are skipped (not shared by everyone); the per-number, per-account and shop-wide limits still apply.
- **Back up `DATA_DIR`.** It holds the database, uploaded photos, receipts, backups, the admin account, session key and audit log, with owner-only permissions (an existing folder is tightened to 700 at start).

## Orders, prices and stock

- **Orders are stored on the server**, in a SQLite database in `DATA_DIR/shop.db`. It runs in WAL mode with full sync on commit, so a confirmed order survives a power cut.
- **The server works out what the customer pays.** It takes each line's product, bed size and quantity and computes the unit prices, totals and fees from the catalogue. A forged price in the request is ignored.
- **Stock is reserved in the same transaction** (`UPDATE … WHERE stock >= qty`), so two customers can never both buy the last set. Cancelling an order puts its stock back.
- **Every order's phone number is proved:** with Phone check "SMS code", by a signed, 30-minute token issued by `/api/otp/verify` (a number not verified by SMS can't be put on an order, except on a card order, where the card payment is the proof and the order counts only once Stripe says it is paid); with "WhatsApp (free)", afterwards, by the customer's WhatsApp message or the owner's call, with the caps and auto-cancel above.
- **One checkout attempt = one order.** The browser sends a random checkout reference, and a double tap or network retry gets the same order back.
- **Status changes follow allowed steps.** For example, a confirmed order cannot jump to delivered, and cancelled or delivered orders are final. Each change is recorded per order and in the audit log.
- **Track Order needs the order number and the phone number on it** (or one it had before the owner changed it), and shows status and delivery only (no address, email or full name). Lookups are limited per address and per order number.
- **Bank-transfer receipts** (PNG, JPEG, WebP or PDF, checked by their first bytes, max 5 MB) are stored on the server and shown only to the admin, sandboxed. A new upload keeps the earlier ones (`receipts/<order>.v<n>.<ext>`).

## Settings and keys

- **Branding, bank details, courier keys and SMS gateway settings** are stored on the server, so every visitor sees the same shop. The bank details are never sent to visitors (see "Bank transfer without the account on the website").
- **Keys are write-only.** The admin hub gets them back blank, with a "saved" flag. A save with a blank key keeps the stored one, and `null` clears it.
- **A key follows its host:** changing the Infobip or webhook address without a new key drops the old key.
- **"Test connection" fills blank keys from the saved ones on the server**, so the keys never travel back to a browser. A saved key is only filled in for the host it was saved for: a test aimed at a new address must bring its own key.

## Backups

When something changes (see the deployment guide), the shop backs itself up:

- **What changed is counted by the database itself** (migration 16: triggers on the shop's tables add to `data_changes`, one row per area), so no write path is missed; files written beside it (product photos) are counted by `markChanged`. Reads, sign-ins (a passkey's counter, an accountant's last sign-in), sign-outs, the chat's "seen" marks, caches, counters and rate limits are not counted. The audit log records why each backup ran (`changes`, `weekly-check`, `manual`, `startup`) and how many changes it held per area, never what they were. A backup's mark is taken before it starts and recorded only after it succeeds, so a failure (or a change made while it runs) stays waiting.

- **A consistent database snapshot**, integrity-checked before it is used.
- **CSV flat files.** A cell starting with `= + - @` is prefixed with `'`, so Excel never runs it as a formula.
- **Receipts, photos, expense bills and the audit log**, with a SHA-256 manifest. The stock ledger and product drafts are tables in the database copy; `stock_moves.csv` lists the ledger for Excel.
- **Encryption (strongly recommended):** AES-256-GCM, with the key derived by scrypt (cost 2^17) from the backup password. The Admin Hub turns amber ("Backups are emailed unencrypted… Protect them with a password in Settings → System & backups"), and the log warns, while backups are emailed unencrypted or a server-set password is shorter than 12 characters.
- **The backup password (`src/lib/server/backupSecret.ts`, Settings → System & backups → "Protect backups with a password"):**
  - **Chosen in the hub, owner only:** `GET/POST /api/admin/backup/passphrase` (requireAdmin: an accountant gets 403; same-origin; `readJsonBody` capped at 2 KB; fields allow-listed per action; 30 changes an hour; `handleRouteError`; `Cache-Control: no-store`). **Make one for me** (`generate`) makes six words from the built-in EFF large wordlist (7,772 words) and two digits with `crypto.randomInt` (about 84 bits); it is the only reply that ever carries the password, and nothing changes until **I saved it** (`confirm`, within 30 minutes). **Type your own** (`set`): 12 to 256 characters, typed twice, at least 5 different characters, no control characters or edge spaces.
  - **Changing it** (`change`, or `confirm` while one is set) asks for the hub password again (`confirmOwner`, a passkey sign-in is not enough, under the sign-in rate limit). Audited as `backup.passphrase_set` / `backup.passphrase_changed` (who, how, fingerprint; never the value) before the reply says it is done.
  - **Storage:** `DATA_DIR/backup-secret.json`, owner-only (0600, written atomically with `writePrivateFile`), never in the database and never in a backup (`createBackup` packs only `shop.db` and the shop's folders, as for `drive-secrets.json`; the restore accepts only known names). The old password is not kept; a restore copies the running shop's file (without a password waiting to be confirmed) into the restored folder, so a restored shop keeps encrypting.
  - **Fingerprints:** SHA-256 of `scrypt(password, fixed salt, N=2^17)`, first 12 hex characters: no quicker to guess from than the backup itself. Each encrypted backup's header carries `fp` and `fpSet` (the day the password was set); the file keeps earlier fingerprints with their days. The restore script checks the fingerprint before reading the backup and refuses a different password with the day of the one needed; a matching fingerprint with bad data is reported as damage.
  - **`BACKUP_PASSPHRASE` wins** when set: the hub shows "Set on the server" and refuses changes (409).
  - **Never logged:** `logEvent` and the audit log remove the current password (and one waiting to be confirmed, and `BACKUP_PASSPHRASE`) wherever it appears, whatever the field name (`addRedactedValue` in `log.ts`), besides the usual redaction of `pass…` fields.
- **Courier and SMS keys are blanked** in the backup's copy of the database (and the copy is vacuumed, so the old values are not left in free pages). Re-enter them after a restore.
- **A failure is emailed** when it starts, when the error changes and then once a day; the shop retries hourly.
- **Delivered by email over TLS** (STARTTLS is required, so the SMTP password is never sent in clear).
- **Kept on the server too:** every backup of the last 14 days (never fewer than the newest 14); when the disk is tight (no room for three more), all of the last 24 hours and then the newest of each UAE day. Ages count from the 14th newest backup (or the clock, when earlier), never from the clock alone, so a clock that jumps forward makes nothing look old until 14 backups carry the wrong time; at most 5 are removed a run; and none at all while Google Drive has seen the server's clock more than a day from Google's (kv `backup:clock`, below).
- **Session keys and the admin account are not in backups.** Restore accepts only the known file names, so a crafted backup cannot plant a key or an admin account.
- **Passkeys and recovery codes are in backups** (public keys and code hashes only, in the database). On restore the codes are voided and the passkeys switched off until the owner reviews them, because the backup may predate a revocation (see "After a restore" above). Unfinished passkey challenges are removed from the copy.
- **Restore checks before anything is used:** every file against the manifest, and the database's integrity. An encrypted backup is also authenticated (GCM); a plain `.tar.gz` can only be checked for damage, not tampering.
- **Off-server copies in Google Drive (opt-in, `src/lib/server/driveBackup.ts`):**
  - **Only encrypted copies:** switching it on is refused without a backup password; connecting before there is one marks copies to switch on as soon as one is set (audited). A copy is never made of a file that does not start with the encrypted header, and a missing passphrase later pauses copies (an owner alert).
  - **Or a service account (shared drives), no OAuth consent:** each copy signs a one-hour JWT (RS256, `node:crypto`, scope `https://www.googleapis.com/auth/drive`; the service account sees only what is shared with it) and trades it at `https://oauth2.googleapis.com/token` (JWT bearer grant). The access token is kept in memory only, until a minute before it expires.
  - **Connect my Google Drive (recommended; OAuth 2.0 device flow):** the owner's own OAuth client (type "TVs and Limited Input devices"). `POST https://oauth2.googleapis.com/device/code` with scope `https://www.googleapis.com/auth/drive.file` only (the shop sees only files it made; Google lists it as non-sensitive, and it is one of the scopes the device flow allows). The hub shows the user code and Google's verification address (used as a link only if it is https on google.com, else `https://www.google.com/device`). The server polls `https://oauth2.googleapis.com/token` (grant `urn:ietf:params:oauth:grant-type:device_code`) only when the hub asks and never sooner than Google's `interval` (+5 s on each `slow_down`; the next poll time is claimed first, so two tabs make one request per interval), and stops at `expires_in`, `access_denied` or `expired_token`. An answer that arrives after Cancel or a new Connect (the device code in hand is no longer the pending one) is dropped without saving anything. On success the connection is saved first (a refresh token is never thrown away), the connected account's email is read with Drive's `about.get` (`fields=user(emailAddress)`, allowed by `drive.file`: no extra permission) to show "Connected to …", then the shop makes its own folder "Beautiful UAE Home backups" (or keeps the saved one while the same client still sees it); if Google fails to make it then, the next copy or Test connection makes it. A pasted folder is never used in this mode (drive.file can't see it). Access tokens come from the refresh token (grant `refresh_token`), in memory only; `invalid_grant` (revoked, or 7 days in Testing) marks the setting "Reconnect Google Drive" and raises the `drive_backup` alert. **Disconnect** first asks Google to revoke the refresh token (`POST https://oauth2.googleapis.com/revoke`, best effort, through `safeRequest`, audited as `backup.drive_revoked` with the outcome, never the token), then forgets it here whatever Google answered.
  - **Its secrets:** the client secret, the refresh token and a device sign-in in progress are kept in `DATA_DIR/drive-secrets.json` (see "The secrets file" below), never in a reply (the hub sees the client id, "secret saved" and "connected"), blanked or left out in every backup, and never logged (`logEvent` also removes `1//…` refresh tokens and `GOCSPX-…` client secrets by shape). **Copy restore details** (`POST /api/admin/backup/drive/restore-details`) shows them as env-file lines only after the current password (a recent passkey sign-in is not enough), under the sign-in rate limit, and writes `backup.drive_details_revealed` to the audit log before answering.
  - **The setup wizard:** `PUT /api/admin/backup/drive/wizard` (owner only, 1 KB, allow-listed `done` steps and a Google Cloud project id checked against Google's format) keeps the ticks and the project id in kv `backup:drive-wizard` (nothing secret). The console links are fixed `https://console.cloud.google.com/…` addresses with `?project=` URL-encoded; they open in a new tab with `rel="noopener noreferrer"`. Google's client file (`client_secret_….json`) is read in the browser only, to fill the client ID and secret (a service account key or a Web client is refused); the server checks both again as before.
  - **Fixed hosts only:** `oauth2.googleapis.com` and `www.googleapis.com`, through `safeRequest` (no redirects, timeouts, reply size caps, public addresses only). The resumable session address Google returns is used only if it is `https://www.googleapis.com/upload/drive/v3/files?…upload_id=…`. The owner chooses a folder id, never an address. `BUH_TEST_GOOGLE_API` (tests only, like `BUH_TEST_STRIPE_API`, `BUH_TEST_ANTHROPIC_API` and `BUH_TEST_GEMINI_API`: `src/lib/server/testStandIn.ts`) accepts nothing but a plain-http loopback address, and a production build (`NODE_ENV=production`, as in the image) ignores it unless the test server's own flag `BUH_TEST_SERVER=1` is set; the restore script follows the same rule.
  - **Streamed and verified:** a resumable upload (`uploadType=resumable`, `supportsAllDrives=true`) in 8 MB pieces read from disk. The file is opened once and its size, MD5 and every piece come from that open file (a backup replaced at the same path meanwhile is not mixed in; one cut short fails instead of looping). Retries (network, 5xx, 429) are counted only while the upload makes no progress (at most 5 in a row), and a `308` that keeps reporting every byte without finishing counts too. The file's MD5 and size must equal Drive's `md5Checksum` and `size`, otherwise the upload is deleted and the copy fails. Each upload is marked `appProperties.buhBackup=1`.
  - **Not part of the backup:** the copy starts after the backup and is not waited for, so "Back up now" and the backup lock never wait on Google; the hub shows the copy in progress (`copying` in the status, bytes sent of the size). One copy at a time; a backup taken meanwhile is copied next (only the newest waiting one).
  - **Retention** (`driveRetention` in backupPolicy.ts), among the copies this feature uploaded (their Drive file ids are recorded in kv `backup:drive-files`): up to 4 a UAE day for the last 7 days, the newest of each day to 30 days, the newest of each UAE week (Monday to Sunday) to 6 months; over the owner's N (default 60), the newest days are thinned first and the oldest weekly copy, the newest copy and the one just made are never removed. Ages are Google's, never the server's: each upload and the fill-in `files.list` ask for `createdTime` (kept beside the shop's own `at`), and every copy is aged by it against the `createdTime` Google gave the copy just made. A copy recorded before this (no `createdTime`) is dated from a `files.list` of the folder (`fields=nextPageToken,files(id,createdTime)`, only this feature's copies) and is never removed until it is. The server's clock is checked against that same `createdTime`: more than a day apart, nothing is deleted that run (in Drive or on the server), `backup_clock_skew` is logged and audited (`backup.clock_skew`), kv `backup:clock` holds the mark for 7 days (renewed while wrong, ended by a right check or by a clock put back before it), and backup health shows "The server's clock looks wrong — backups are kept, old copies aren't removed until it's fixed." At most 10 are deleted a run. Older ones are deleted by id. A delete that fails for now (no answer, 5xx, 429, 401) is tried at the next copy; one Google refuses for good (403: no longer ours to delete; other 4xx) is no longer tracked and is audited (`backup.drive_remove_failed`), so retention never stalls. A copy that finishes after the account, folder or mode changed is not recorded under the new setting. Nothing else in the folder is ever listed for deletion or deleted.
  - **The secrets file:** the service account's `private_key` and its id, the OAuth client secret, the refresh token and a device sign-in in progress live in `DATA_DIR/drive-secrets.json` (mode 600, written atomically: temp file and rename), never in the database (kv `backup:drive` keeps only the mode, switch, folder, client id and the service account's email). `createBackup` takes only `shop.db` and the shop's folders, and the restore accepts only known names, so no backup (from this image or an older one) can hold them. Secrets the first version kept in kv are moved to the file on start (and before any read), then removed from kv; a backup still blanks any found there (the copy is vacuumed).
  - **The key is a secret:** never in a reply (the hub sees the service account's email), not a settings group (so never in settings history), and never logged: `logEvent` removes any PEM private key, a bare key body (`MII…`) and Google access tokens (`ya29.…`) wherever they appear, and fields named `private_key`/`privateKey` by name. Google's error text is passed on with keys, tokens and JWTs removed.
  - **Failures:** recorded, audited (`backup.drive_failed`), and raised as the owner alert `drive_backup` (monitor.ts); the local backup is unaffected. Saves, tests, copies, deletions and revocations are audited (`backup.drive_saved`, `backup.drive_tested`, `backup.drive_copied`, `backup.drive_removed`, `backup.drive_remove_failed`, `backup.drive_revoked`).
  - **Restore from Drive:** `scripts/restore-backup.mjs --from-drive latest|<name>|list` (in the image, with `scripts/restore-from-drive.mjs`) takes the connection from `BUH_DRIVE_CLIENT_ID`/`BUH_DRIVE_CLIENT_SECRET`/`BUH_DRIVE_REFRESH_TOKEN` (the folder then optional: found by its name among the files this client made) or the key from `BUH_DRIVE_KEY`/`BUH_DRIVE_KEY_FILE` with `BUH_DRIVE_FOLDER`, or from the shop's saved settings (kv `backup:drive` and `drive-secrets.json`; a saved folder id is used only if it is an id). It calls the same two fixed hosts directly (Node `https`, no address a person can choose; a listing stops after 50 pages or at an empty page that repeats its token) and lists only files the shop marked (`appProperties has { key='buhBackup' and value='1' }`) named `buh-backup-<stamp>.tar.gz.enc` and stamped no more than a day ahead. It streams the download to a random name next to the restore (a write error ends it; Ctrl-C or SIGTERM removes it and everything restored so far), checks Drive's size and MD5, refuses a copy that is not encrypted, and then restores it as any encrypted backup (GCM tag, manifest, integrity check), removing the download in every case.
- **Streamed both ways, size-capped:** a backup is packed, compressed and encrypted a piece at a time (written to a temporary name, renamed when complete; the GCM tag is written into its fixed-length header at the end), and the restore decrypts, uncompresses and unpacks one file at a time into its own folder, refusing unknown names and duplicates as they come, bounded by the free disk (256 MB kept free). Nothing restored is used until the tag, every checksum and the database check pass; on any failure everything it wrote is removed. The data backed up may be at most 6 GB (`BACKUP_LIMITS`): the monitor warns from 80%, and beyond it the backup fails (audited, the owner emailed) instead of producing a file too big to restore.

## The customer's order emails (BUH-02.25)

- "Your order is in process" (cash on delivery, when placed) and "Your order is confirmed" (cash on delivery and bank transfer, once the shop has confirmed it) go only to the address typed at checkout, only when the shop's email is set up, and never for a cancelled order (src/lib/server/orderMail.ts).
- Each is claimed on the order before it is sent (`received_emailed_at`, `confirmed_emailed_at`, migration 17, add-only), so two copies of the shop, a retry or a double tap send it once. A failed send releases the claim; every outcome is in the order's history.
- An address can't be flooded: at most 6 order emails a day to one address and 10 per connection (the connection kept only as a hash). The customer's name is cleaned so it can't carry a link (`safeFirstName`).
- The links are built from the shop's configured address only (`NEXT_PUBLIC_APP_URL`), never the request's Host: the WhatsApp confirmation (wa.me) and Track Order (`/?open=track&order=<id>`, which only fills in the order number; Track Order still asks for the phone).
- The log masks the address. Replies go to the shop's contact email.

## Orders and stock

- **The customer is charged the total they saw.** Checkout sends the total it showed; if a price changed meanwhile, the server refuses the order (nothing taken) and checkout reloads the bag with the new total.
- **At most 20 of one product per order, and at most 3 unconfirmed orders per phone**, so one verified number cannot tie up the stock.
- **Stock edits cannot undo a sale:** the Admin Hub sends the stock it showed, and the server refuses the edit (409) if a sale happened in between.
- **Stock moves from the Admin Hub** (`POST /api/admin/products/<id>/stock`: − / +, a typed number, Received stock, Sold out, Undo) are admin-only and same-site, with a 4 KB body cap and an allow-list of fields and reason codes (received, sold offline, damaged, correction).
  - **Idempotent:** each change carries its own key; the same key again returns the first answer and moves nothing; the same key with other numbers is refused (409). A lost answer is retried with the same key.
  - **Never from stale numbers:** each change says what the device saw for every size it changes; if the stock is different now (another device, a sale), nothing is changed (409, "changed on another device"). A typed number must say what was seen.
  - **Recorded before it is reported:** the move (who, why, every size's old → new) is written to `stock_moves` in the same transaction as the stock, then to the audit log, before the answer. The product editor's stock changes are recorded the same way. Undo works once, and only if nothing changed those sizes since.
- **Photos** uploaded from the editor (`POST /api/admin/images`) go through the same checks as every image (PNG, JPEG or WebP by their real bytes, at most 3 MB); the phone shrinks them first. **Drafts** (`/api/admin/products/drafts/<id>`) keep only the editor's own fields, accept only uploaded or https photo links, and are capped at 64 KB; nothing in a draft reaches the shop until it is published through the normal product checks.
- **Duplicate** makes a hidden copy with no stock; its key makes a retried request return the same copy.
- **Bank transfer is hidden until the real account is saved.** The IBAN must be a UAE IBAN that passes the mod-97 check. Even then the account is never on the website, only behind each order's private link.

## Public data and outbound calls added in BUH-02.00.00

- **Public endpoints show only what the shop shows:** `/p/<id>`, `/feeds/meta.csv` and `/sitemap.xml` list visible products only (hidden and removed ones are left out); `/api/events` sends change counters for the catalogue and settings, never order data (the admin stream `/api/admin/events` needs sign-in).
- **Fixed outbound URLs only:** exchange rates (open.er-api.com, daily) and public holiday calendars (calendar.google.com, weekly) are fetched from fixed addresses with timeouts and size caps; replies are validated and a bad match is rejected. Nothing a visitor or admin types is fetched.
- **Settings history never keeps keys:** saved versions have courier and SMS keys blanked; restoring one keeps the keys saved now.
- **SMS codes** are stored hashed (keyed with the shop's own secret), single use, 10 minutes, in the database, so both copies of the shop during an update check them the same way.
- **Customer details at checkout** are remembered in the customer's own browser only (never the phone check), with **Not you? Clear them**.

## Shared links, simple products and the marketplace export (BUH-02.17)

- **Public page `/c/<slug>`:** shows only products on sale (shown and not removed), read on the server; the page never receives hidden products, stock moves or anything about the owner. The slug is the title's words plus 5 random characters (31-letter alphabet, about 28 million choices per title), checked against a pattern before any lookup. It is `noindex` (links made to be sent, and they end), not in the sitemap, and an ended or unknown address shows a plain page with no product data.
- **Counter `POST /api/collections/<slug>`:** `{ kind: 'view' | 'bag' }` only (allow-listed, 256-byte cap), same-origin only (403 otherwise), 60 per address per 10 minutes and 3,000 a minute shop-wide, and it counts nothing on an ended link. It stores two numbers: nothing about the visitor.
- **Admin routes** `GET/POST /api/admin/collections`, `PATCH/DELETE /api/admin/collections/<id>` and `GET /api/admin/exports/marketplace`: `requireAdmin` (door, session, same-site), bodies through `readJsonBody` (16 KB) and an allow-list of fields, errors through `handleRouteError`. Product ids must exist; titles, dates (a real date, not in the past) and the idempotency key are checked. Creating, editing, deleting a shared link and each marketplace export are written to the audit log. The CSV is formula-safe (as every export) and sent `no-store` as a download.
- **Simple products:** the product type is checked on the server (`bedding` or `simple`); a simple product's variants keep only their own fields (bed measurements sent by the browser are dropped) and prices, stock and weights are validated as for sizes. Prices are still computed in fils on the server at checkout.

## Search (SEO) and SKUs

- **New public pages** `/shop/<category>` and `/gifts/<festival>` read only products on sale (as `/api/products`), on the server; an unknown category or festival is the ordinary not-found page. A festival page the owner switched off still answers, with `noindex`. Structured data (JSON-LD) is built from the server's own values (prices in fils → AED, stock per size) and written with `<`, `>`, `&` and line separators escaped, so nothing in a product name can end the script. No ratings or reviews are ever emitted.
- **Kept pages:** the home page (5 minutes) and the category and festival pages (1 minute) are built once and kept in memory (never on disk: the image is read-only), rebuilt on the next visit after any product or settings change, including changes made by the shop's own timers. They hold only what every visitor sees (no cookies or per-visitor data are read while building them; their address comes from `NEXT_PUBLIC_APP_URL`, never a request's Host).
- **robots.txt** disallows `/api/`, `/pay/` and `/invoice/` and names the sitemap. It never names the Admin Hub (its private link, or `/hub`): naming an admin path would only tell a stranger where to look, and those addresses already answer as unknown. Shared links (`/c/…`) stay crawlable so crawlers can read their `noindex`. The sitemap lists only the home, category, festival (not switched off) and product pages.
- **Verification codes** (Google, Bing) are stored as the `content` value only: letters, digits, `-` and `_`, 8–100 characters (a pasted `<meta>` tag is accepted and reduced to its value); anything else is refused, so a code can never inject markup into the home page.
- **IndexNow** is off by default. Its key (32 random hex characters, in the database, so backups carry it) is public by design: it is served at `/indexnow-key.txt` only while IndexNow is on, and only proves that pings come from this site. Pings go to one fixed address (`https://api.indexnow.org/indexnow`) through `safeFetch` (https only, public addresses, no redirects, timeouts, size cap), only for the shop's own address from `NEXT_PUBLIC_APP_URL` (never the Host a visitor sent), gathered for 10 s into one ping, at most 20 an hour, and each is written to the audit log (`seo.indexnow_ping`, paths and status only).
- **Settings → Search (SEO)** is a settings group like the others (`seo`): an allow-list of fields, every text one plain line (control and direction-override characters stripped), capped (title 70, description 200, heading 90, introduction 600), unknown festivals dropped; kept in settings history and backups. Routes `GET/PUT /api/admin/seo` and `PUT /api/admin/seo/product`: `requireAdmin` (owner only), `readJsonBody` (64 KB / 8 KB), allow-listed fields, `handleRouteError`; saves are audited (`settings.updated`, field names only; product overrides as `product.updated`).
- **SKUs** are made and checked on the server: capitals, digits and dashes, at most 40, unique across every product ignoring case (a duplicate is refused with 409 and the next free one); an SKU already saved is never rewritten. The running number is in the database (kv `sku:counter`, carried by backups) and only goes up. `POST /api/admin/products/sku-suggest` (4 KB, allow-list, takes nothing) and `GET/POST /api/admin/products/sku-fill` (one transaction, audited as `product.skus_filled` before it is reported) are owner only. A changed SKU is in the product's audit entry (from → to). The marketplace code (`marketplaceSku`, the id-based code a product was exported under before it had an SKU) is set by the server only, never taken from a request, and never sent to shoppers.

## Known limits (next steps)

- **One admin account; no staff roles yet.**
- **One server process, except briefly during an update.** Phone codes are stored hashed in the database, so both copies accept them; rate limits are per process, so during the overlap of an update a limit can briefly allow up to twice its count.
